# Auditing without converting

`audit.py` says what is wrong with a file and changes nothing. It takes Word and Markdown sources, PowerPoint decks, HTML pages, EPUBs, and PDFs, in any mix, and writes two things: `audit.csv`, one finding per row, and `audit.md`, the same findings as a report a person reads.

```bash
python3 $T/bin/audit.py ~/books/nursing            # everything in a directory
python3 $T/bin/audit.py syllabus.pdf book.epub -o ~/reports --report-docx
```

It depends on `lib/` and on Pandoc, to read a source. `pypdf` (for PDFs), epubcheck, the Nu HTML checker, and veraPDF are used when present and reported as absent when not; `--quick` skips the external ones. `--wcag` checks against WCAG's criteria a machine can test as well, WCAG 2.1 AA unless `--wcag-version` and `--wcag-level` say otherwise, as the output check does: each HTML page and EPUB with [axe-core](checking.md#axe-cores-wcag-checks), in one browser for all of them, which needs the optional Playwright, and each PDF against [veraPDF's WCAG 2.2 machine profile](checking.md#verapdfs-wcag-22-checks). What they find is a note, never an error, one for each rule a page or a PDF fails, counting its elements or its failed checks, and the report has a section on the pages and one for each PDF saying whether the checks ran, and when they didn't, why. `--best-practice` adds axe-core's best practices, and `--experimental` the rules it's still trying ([Checking](checking.md#axe-cores-wcag-checks)). `--verbose` makes each element axe-core names and each check veraPDF failed a note, with what the file has there (an element's markup, a link's address, the line repeated characters are on), and an item in the section under its rule's.

## What it checks, by kind of file

**A Word or Markdown source** is read by Pandoc with no filter, so the audit sees the author's file as it is, one file as one document (a `project.yaml` beside it supplies the book's language): images with no alt text and no `{.decorative}` marker, alt text that holds a file name, says nothing, was generated by Office, looks copied from a web page with the picture, or is only a credit, by the rules a deck's pictures are judged by (`source-image-alt-is-file-name`, `-placeholder`, `-auto-generated`, `-page-title`, and `-credit`), and, as a note, one alt text on different images in the file (`source-image-alt-shared`), told apart by their files' content, a figure's image whose alt text is the figure's caption word for word (`source-image-alt-is-caption`), as Pandoc gives a Markdown figure written `![caption](file)` with no alt text of its own, which a tagged PDF says twice, as the caption and as the picture's description, and which describes nothing the caption doesn't, where no other rule finds more to say of the words (give it alt text after the image, `{alt="..."}`; a row of `image-alt.csv` describes it in the book's outputs, but the audit, which reads the file as it is, still reports it), tables with no header row, no marker, and no first column that keys the rows, links whose text is their own URL and that carry no `aria-label` (with one, the accessible name is the label), headings that skip a level, raw HTML the conversion would pass through untouched, math ending in a thin space (which can't be written back as Markdown), and a missing title or language. A Word source adds what the [table census](architecture.md) can say: for each data table, the headers the run would guess and why, or that it couldn't settle them.

**A PowerPoint deck** gets the checks a slides run makes ([Slides](slides.md#whats-checked)): what PowerPoint's own Accessibility Checker reports (slides with no title, objects with no alt text, tables with no header row, sections with the default name, merged cells, reading order, media, duplicate titles and section names), alt text that holds a file name, says nothing, was generated by Office, was copied from a web page with the picture, is only a credit, or runs long, one alt text on copies of a picture cropped to show different parts or on different pictures, a missing language or title, hidden slides, bare links, diagrams drawn from loose shapes or columns laid out with tabs, a font a license restricts, and XML PowerPoint can't read as written. The audit uses the default length limit and placeholders, and looks at each deck alone, so it doesn't name a deck set to embed its fonts that uses a font another deck embeds restricted, without embedding it (`pptx-font-unembedded`), as a run of `convert.py` on the decks does; that run uses the project's limit and placeholders too.

**An HTML page or an EPUB** goes through the [output check](checking.md) as it is, plus the validators when they're installed.

**A PDF** gets the simple report: what the file states about itself, read with `pypdf`, and what that implies. Title, author, language, dates, producer, PDF version, size and SHA-256; XMP metadata and its fields; what the file *claims* (PDF/UA-1 or -2, PDF/A) as distinct from what it is; whether it's tagged and has a structure tree, with a count of tags by type; the bookmark outline; pages with no extractable text, which are scans; fonts and whether they're embedded; encryption. A claim is reported as a claim: "claims PDF/UA-2" is a fact about the file, and whether it *is* PDF/UA-2 is veraPDF's to say, which the audit runs when it finds it. Ace stays by hand.

## What a Markdown file's YAML means to the audit

Each file is read as its own document, so a YAML block applies to the file it heads: its `title`, its `lang`, and nothing else's. A book whose files were written to be concatenated by a Pandoc command line, with one `_preamble.md` carrying the YAML for all of them, is read one file at a time here, and the other files have no YAML as far as the audit can see. The book's facts live in `project.yaml`, which the audit reads when it sits beside the files: `language` there answers the language question for every file. That is the only configuration the audit uses, and it's optional; `conversion.yaml` and `packaging.yaml` are the conversion's business. The audit could instead take the first file's YAML as the book's when `contents` gives an order, but that would make a report depend on a guess the reader can't see; `project.yaml` says the same thing in the open.

## The findings format

`audit.csv` has these columns, in this order:

`Where, Check, Detail, File, Kind, Severity, Standard, Tool, Fix`

The first three are what `output-check.csv` has always carried, so anything reading that today reads this. `Kind` is `source-docx`, `source-md`, `source-pptx`, `html`, `epub`, `pdf`, or `pptx` (a PowerPoint file a slides run wrote, a deck's copy or a `pptx` target's file, in its `output-check.csv`). `Severity` is `error`, `warning`, or `note`, so a validator's failure and a "worth a look" don't read the same. `Standard` names the criterion when there is one, in a form that says which standard and how strict: for WCAG, the lowest 2.x version the success criterion appears in, its number, and its level (`WCAG 2.0 SC 1.3.1 (A)`, `WCAG 2.1 SC 1.4.10 (AA)`); for PDF/UA, the clause of ISO 14289-1 (`PDF/UA-1 clause 7.1`); `EPUB 3.3`; `HTML Living Standard`. It's what turns a finding into an argument with a vendor. `Tool` is who said so: `oer`, `census`, `epubcheck`, `vnu`, `verapdf`. `Fix` is where the fix lives, `source`, `sidecar`, `manual`, or `tool`, which is the column to sort by. Every check's meaning, severity, standard, and usual fix are declared once, in `lib/findings.py`; `output-check.csv` from a conversion now uses the same columns.

## The report, and when it's stale

`audit.md` opens with the date and the tool's version, then every input with its size and SHA-256, then a summary (counts by severity and by check, each check explained), the findings grouped by file, and for each PDF its metadata and claims. The hashes are how you know a report is current: if a file's hash has changed, the report is stale for it. A stable file name, rather than one with a date in it, is what makes reports diffable and linkable; the date is inside.

The same hashes key `audit-cache.json` beside the report. Run again with nothing changed, and with the options the report was made with (`--quick` and `--wcag`), the audit says so at the prompt (`Nothing has changed since the audit of <date>; audit.md is current`) and leaves the report alone, so its date stays the date of the audit it records; the exit code still reflects the findings. With other options, the report is made again, and a file read with another `--quick` than this run's is read again, since the validators' findings are among a file's or aren't. A run with `--wcag` makes the report again however little has changed, since what its checks find turns on what's installed too, which only each check's own part of the cache asks after, as it runs. axe-core's results on the pages and EPUBs are kept in the cache, each page's with every file its check read: the page itself, its stylesheets, pictures, fonts, and frames, and the names of those that weren't there. A page is checked again only when one of those reads otherwise now (a file that wasn't there is), or when axe-core (its file's SHA-256), Playwright (whose version decides its Chromium's), the rules (`--wcag-version`, `--wcag-level`, `--best-practice`, `--experimental`), `--verbose`, or TextbookImprover's own check has changed; an EPUB's content documents are each kept on their own, so an EPUB made again has only those that changed checked. The summary says how many weren't checked again and since when, and with none to check, no browser starts. A page the check gave up on, past its time, isn't kept. One setup is kept at a time: an audit with other rules checks every page again and keeps those results instead. veraPDF's WCAG findings are kept too, the rules of its WCAG profile each PDF failed, with their failed checks, by where the PDF is and its SHA-256, so a PDF made again replaces its own, and one renamed or copied is found by its SHA-256. A PDF is given the profile again only when it has changed, or when one of these has: veraPDF (its launcher, by where it is and its SHA-256, and what its `--version` says), the Java it runs (`JAVACMD`, `JAVA_HOME`, the `java` on the path, `JAVA_OPTS`, and the options any JVM picks up), the folder `VERAPDF_WCAG` names (each file in it, by its SHA-256), `CLASSPATH_PREFIX` as it's set, or TextbookImprover's own check. What's reported of the rules kept is decided as a run's is, so another `--wcag-version`, `--wcag-level`, or `--verbose` needs no run of veraPDF. Nothing is kept from a run with a warning, or from a PDF written again while veraPDF read it, and with a veraPDF that doesn't say which it is (its `--version`), nothing is kept or read. The PDF's section says when it wasn't checked again, and since when. A part of the cache, axe-core's, Ace's, or veraPDF's, that isn't what an audit wrote, as after an edit by hand, is started again. With some inputs changed, only those are read again and the report is rewritten. `--force` reads and checks everything, `--no-cache` ignores the cache both ways. A PDF is still read every time, since its metadata section is built fresh each time, and veraPDF's PDF/UA checks run on it each time.

Markdown is the report's own form. `--report-html` also writes `audit.html`, the report as a page with the pipeline's own stylesheet embedded; `--report-docx` also writes `audit.docx`, declared as the current Word format so Word treats it as a current file and its own Accessibility Checker runs on it (Pandoc's own Word output opens in Compatibility Mode, which turns that checker off). The switches are named for the report's format, not the input's: the audit reads any mix of files whatever it writes.

The reports go in the first folder given unless `-o` names another, so an audit of a folder run again finds the last one's reports there. None of them is read as a file of the book: in a folder given, a report an audit wrote, `audit.md`, `audit.html`, or `audit.docx`, known by its heading and the line that dates it, is passed over, and one this audit is to write over isn't read even when it's named; a report named that the audit doesn't write is read as asked. Nor does the audit write over a file of the book's: in the folder it writes to, a file by the name of one it writes (`audit.csv` and `audit.md`, and `audit.html` and `audit.docx` when asked for) that an audit didn't write stops it before it writes anything, saying so. With `-o` another folder, a chapter named `audit.md` is read with the rest of the book.

What a file says is text in every form of the report: a heading, alt text, or a PDF's title that holds markup, `<script>` or `[a link](javascript:...)`, is written into `audit.md` with each character that Markdown could read as markup escaped, and shows as written in `audit.html` and `audit.docx`. Pandoc renders them from `audit.md` without raw HTML, raw TeX, or smart punctuation, and in its sandbox (`--sandbox`), so it reads nothing but the report and the stylesheet.

## `convert.py --check-only`

The conversion's own reports (media unresolved, table headers, captions, alt text, page names) come from the steps before rendering. `convert.py --check-only` runs those steps and stops: no output directory, nothing packaged. It's the audit from the conversion's point of view, with the sidecars applied; `audit.py` is the source's own view, with nothing applied.
