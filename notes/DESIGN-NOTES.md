# Design notes

Decisions about TextbookImprover itself whose reasons aren't obvious from the code: why it's built this way, what was tried and dropped, and what a rule was measured against. What the code does is in [the documentation](../docs/) and the [changelog](../CHANGELOG.md); what's planned is in the [roadmap](../ROADMAP.md). An entry states the decision, then the reason, then the evidence (what was measured, on which books, and when), then where it lives in the code. What other software does, which many of these decisions answer, is in the other files of this folder; [README.md](README.md) lists them.

## Principles

**The Word round trip matters most.** The pipeline remediates Word files as a foundation for work in Word, so losing nothing on the way from a Word file and back is worth reinventing parts of Pandoc, at least until Pandoc changes. Word as a target for a book from another format matters less: preserve what can be preserved, but not by means that break when the document is edited or reordered (set 2026-09-25).

**Be transparent about losses rather than piling up workarounds.** A loss is documented, and the run warns of it (`fidelity.csv`) (set 2026-09-25).

**Information is never carried in a Word file by order alone.** Carried by order, the worst case is information on the wrong element, which happened with tables. Carried by a fingerprint of the content or by a mark on the element, the worst case is what happens without it, so best effort beats nothing (set 2026-09-25).

**Say which claims are verified and which rest on documentation**, in the docs, the code's comments, and the changelog alike, and link the publicly accessible documentation a claim rests on, for readers and for whoever works on the code later (set 2026-09-25). The case at the time: nothing had been tested with JAWS, and the bookmark convention a Word target writes for a table's headers is from Freedom Scientific's own pages, one labeled an older technique, and a 2017 bulletin. `docs/formats.md` says which is which, and still said of both "Neither is tested with JAWS here" on 2026-11-11.

**A rating in `docs/formats.md` is measured, never reasoned.** Writing that page meant measuring the paths nobody had taken, and each thin rating turned up a defect (by 0.8, 2026-10-03): an AsciiDoc book's EPUB failed epubcheck (layout attributes on blocks), DCIC's Markdown never read back (a MathJax 2 rendering nested eleven spans deep, which Pandoc's Markdown reader can't get through), DCIC's EPUB failed on ids with spaces, and a `pdf` or `docx` target did nothing without saying so. A rating written without the measurement would have been wrong in each case.

**Anything that might run side by side writes only in a folder of its own, and hands its messages back for the run to print in order**, as a target's folder and the test suites' cases do already; the rule is cheap to keep and costly to add later (`ROADMAP.md`, "A book's targets side by side"). For a user the gain from more than one processor is in targets, a PDF above all, not in pages: the suites' books spend 26 s in `pandoc -t pdf` and 6 s measuring the page for each PDF target, and seconds on everything else (measured 2026-11-10). So the first slice, when it comes, is a book's targets side by side and the output check's three validators, each writing in its own folder, behind a `-j` that defaults to 1; pages side by side is the larger change for the smaller gain (2026-11-11).

## The pipeline: pages, intermediates, and targets

### Pages

**The filter runs once per page, never over a concatenated book.** `figures-and-tables.lua` takes its document's name from `PANDOC_STATE.input_files[1]`, and the resolved header declarations, the table keys, and the media keys all hang off it; run over a concatenated book, no declaration matches. So the filter runs once per page with `-t json`, writing `<page>.filtered.json`, and everything else (the HTML render, the Markdown writer, the splitter, the EPUB assembler) reads that. The one thing the filter looks at `FORMAT` for, the byline going into the head only for HTML writers, treats `json` as HTML-bound.

**Every page-to-be is found before anything is read, and two sources that would be one page stop the run.** With several source formats, `ch1.md` and `ch1.adoc` were both page `ch1`, one silently overwriting the other's intermediate and every page-keyed sidecar describing whichever won. Two more of the kind were found with it (by 0.8, 2026-10-03): `image-alt.csv`'s match without the extension lent one image's alt text to another that shared its name, and two images' names met only once each was made safe for a link, which the media gate stops on (Links, ids, and titles, below).

**White space in marks is cleaned in the shared filter, for every source and output, not in one target's.** A pass of `figures-and-tables.lua` after the first, before anything reads a table's cells or its words, makes emphasis, bold, a subscript, a superscript, small capitals, or a span with no attributes that holds nothing but white space (Python's whitespace, U+00A0 among it, as the filter's `WIDE_SPACES` has it) that white space, drops an underline or a strikeout holding nothing at all, and empties a table's cell holding nothing but white space. A pass at the end (`white_last`) does the marks again, for one that `Link` has since emptied of a link with no text (`<em><a href="…"> </a></em>`), then makes two spaces side by side one (`one_space`). A mark's own space at its edge goes, as a reader would move it out, but only from a list holding something else, so no mark is emptied: an underline holding only a space keeps it, its line drawn under it, and so does a span with an attribute, the spaces either side staying too. Two spaces with an empty span between them (an anchor) stay two; _Instrumental Analysis_ has none. The cleaning was first built in `pdf-target.lua`, for the PDF alone, and moved when the same marks turned up as double spaces in the book's Word files, 218 of them, 212 from such marks and links (2026-10-19).

### The split

**The split runs on the filtered intermediate, after the filter and before the render.** A page is the unit `contents` arranges, and a page is a file, so the split step makes pages out of a file. It can't come first, because the filter is per-document: the pre-pass hands it declarations keyed by source file and table index, the alt-text keys carry the source stem, and the reports name the source, and on a file already cut all of that misses. Split after the filter, the pieces carry remediated tables while the reports still name the file the author has to fix. Everything downstream sees ordinary pages.

**A piece is named `<source>--<heading>`, and `page-names.csv` gives a piece's whole name.** The derived name survives moving the section and changes when the heading does. A heading that repeats under a different parent takes the parent's name as well; under the same parent, a number. `page-names.csv` is keyed on the source, the headings above (joined with ` > `), and the heading's text, with a `position` column that the prefilled rows fill in only where those three can't tell pieces apart, the one field that moving a section changes. The sidecar gives the whole name, not a suffix, so that a full rename is possible; what that costs is finding the last run's pieces to replace, and the run keeps their list in `page-names-report.csv` for that. `--` in a source's own name is reserved and refused.

**Provenance is in the page.** Each piece records `source-page`, `source-title`, `page-part`, `page-position`, and one `page-parent` per enclosing heading, in its metadata and as `<meta>` in the head, so the packager (which reads only HTML) and the assembler (which reads the intermediate) both group pieces under their headings without a tree. Groups nest by position, not by title path, so two modules' "Introduction" groups stay apart. A heading with nothing of its own before its first child is a group, not a page; an empty heading cuts nothing and is nobody's parent; a book that is one source isn't wrapped in a group for the source, which had pushed every page below the default `toc_depth`. In the EPUB, a heading's own introduction page opens its group rather than repeating the heading.

**The source's intermediate is removed once its pieces exist.** Left behind, the assembler's glob took it for a page holding the whole book. (When content precedes the first cut, that page takes the source's name and overwrites it instead.) The consequence: running the splitter again by hand needs `convert.py` to regenerate the file first.

**A piece inherits what describes a page, not the source document's front matter.** The split copies the source's metadata to every piece, and the page template renders `subtitle`, `date`, and `include-before`, so the first section of the Markdown textbook opened with the book's copyright line. Those fields stay on the source's own opening page, which is the title page.

**Split pieces are adopted as sources by renaming them.** `adopt-pages.py` writes a new book directory with each `a--b` page renamed `a-b`, every reference following, and the split's provenance removed from each head, since read back it would describe a split that no longer applies. A caption keyed on its position rather than its label won't find its table afterward and reappears in the missing report, which is the honest outcome (`docs/splitting.md`).

### Contents and groups

**The outline matcher finds a page by name, then by title.** A filename derived from each heading is how OpenStax names its files, and matching by that alone is why files named `BC-01` or cut by the split could never match. The matcher also matches a page's own title, normalized the way a heading is, settling a title two pages share by provenance (the page from the source the rest of the group came from) and then by reading order, which the outline is in. A top-level entry that is itself a page keeps its children as pages when they are pages. Blank entries are skipped; an entry over 200 characters is reported and skipped rather than matched against every title in the book. Pages the outline never names are appended under their source's title.

**The contents tree and the filename guess live in one module, `lib/bookcontents.py`, and an EPUB's outline is read by one, `lib/epubsource.py`.** `project.contents` is declared once because a cartridge's organization and an EPUB's table of contents are the same structure expressed twice, and the code that reads it has to be shared for the same reason: the two halves of the pipeline share a configuration and the book's table of contents, and nothing else. `--toc` reads an EPUB through `lib/epubsource.py`, which `unpack-epub.py` uses too, so the two can't disagree about a book's outline.

**A group is whatever the author calls it.** Chapter, unit, book of a series: the tools say "group" and treat it as a heading at its depth. `toc_depth` is Pandoc's `--toc-depth`, passed through; what the assembler adds is deciding the levels, so a top-level group or page is 1 and a page's own headings continue below its entry, whatever file each came from.

**Roles are the pipeline's vocabulary for LaTeX's four division commands.** `role` on a `contents` entry (`front`, `main`, `appendix`, `back`), inherited by a group's pages, is what `\frontmatter`, `\mainmatter`, `\appendix`, and `\backmatter` mean; the split reads those and `{.appendix}` into a page's provenance (the filter records one on a heading it promotes, or in a page's own raw block), and the guess of a book's contents uses them, so a book written for a Pandoc PDF build gets its parts right with no declaration. Numbering counts the way a printed book does; a target can say `on` or `off` for itself; the packager follows the book. Page headings are numbered too, in HTML as in the tables of contents and the EPUB.

### Targets and their intermediates

**Every target is built, and the driver knows which intermediates they share.** `read-conversion-config.py` resolves each target; the schema's `stage` attribute on a setting says whether it changes the filtered intermediate, and targets whose filter-stage settings (and variant files) agree share one. `build-epub.py` finds the `epub3` targets for itself; the packager reads the first HTML target's directory.

**Every target writes into its own directory, and the packager takes `--pages`** (since 0.5, 2026-09-19). The only reason pages had ever been written beside the sources was that the packager read its configuration and its pages from one directory. Once that was split, nothing argued for the old layout; the change is marked Breaking because a v0.4 directory looks different after one run. `output_dir: .` keeps the old layout for anyone who wants it, except for a book with HTML sources, where it would overwrite them and is refused.

**An edition is a variant file or a passage.** `<stem>.<target>.<ext>` replaces a page for one target and goes into that target's fingerprint, so it gets its own intermediates; a fenced div with `targets=` (names keep, `!name` excludes) keeps a passage for some targets, resolved at render time so the shared intermediate stays shared. `title_block: off` leaves a page's subtitle, date, and `include-before` out for a target. For an HTML source the plan is Jinja's block syntax, not the engine (`ROADMAP.md`). An AsciiDoc file is a variant like any other; until late in the work on HTML and EPUB input, `ch1.print.adoc` became a page of its own called `ch1.print`.

### Sources, finished pages, and generated pages

**Every `.html` beside the sources is a source; a finished page goes in `_pt/`** (since 0.7, 2026-09-25). Before HTML was a source format, an `.html` with no `.docx` behind it was a finished page. A marker in the contents (`convert: true`) came first and was retired before release: a first run had no contents to carry it, and an HTML book shouldn't need one. The pass-through directory (`_pt/`, or what `passthrough` in `project.yaml` names) holds finished `.html`, copied as it stands, and supplementary `.md`, converted with the sources. Its files resolve their references from the book's directory, so moving a page there changes none of its links. An `.md` beside a same-named `.docx` is still the v0.1 leftover, and an `.html` named after another source is what a target writing beside the sources left.

**`generate:` is the mechanism for pages the run writes** (the contents page today; a title page from project metadata and an index are on the roadmap), rather than reserved page names, so nothing collides with an author's file. The `notes` page from `notes.placement: book` predates that and keeps its name; `contents` may place it.

## Configuration, sidecars, and reports

### Configuration

**Derived values are never written into a generated config.** The writer emits a setting's _declared_ default, not the value resolving would derive from it. A filename worked out from the book's identifier, written into the file as a literal, stops following the identifier the moment either changes. In general: if a value is computed, the config holds the empty default and the setting's description says what it derives to.

**`--allow-unknown-keys` keeps the values it doesn't understand.** A reader that drops what it can't parse and then rewrites the file destroys exactly the settings it was being lenient about.

**Any path that comes from configuration goes through `resolve_path`, and a path the configuration names but the run can't read is an error.** `convert.py` built `"$PWD/$name"` unconditionally, so an absolute sidecar setting became `/book//srv/corrections/table-captions.csv`. The book converted, every correction in the file was discarded, the tables reappeared in the missing report as though nobody had written a caption, and the only trace was an instruction telling the user to append their work to a path that didn't exist. So a path is resolved through the helper, never by prefixing; and an unreadable path the configuration names stops the run, because the failure is otherwise invisible and destroys work.

**An empty value in the configuration is a value, so nothing that consumes one writes `x or default`.** The configuration library resolved `unsorted_title: ""` correctly, and `build-cartridge.py` undid it two lines later. Translating values without auditing how they're consumed is the shape of that mistake, a class and not an incident; it's worth a search for `.get(...) or ` whenever the library gains a caller.

**The book is named in `project.yaml`, which the first run writes as a sample; a `project:` block in `conversion.yaml` or `packaging.yaml` is still allowed** (2026-10-09). The alternative weighed was conversion reading `packaging.yaml`'s block. The configuration was split into three files to keep the two halves separable (v0.2 removed the last coupling between them, which was the configuration); `includes` is a cross-reference, not shared settings, and the EPUB, though an archive, is one rendering of the book, so the separation holds where it matters, and conversion reading the packager's file would undo it. So the first run writes `project.yaml`'s sample and prints the commands for the packaging and conversion samples, and a target that writes a book with no name configured only warns when something can be guessed from the input. The rule for a block: no NOTE when the name is found in the file the half reads, since a book that uses only packaging or only conversion shouldn't need `project.yaml`; a NOTE when both `conversion.yaml` and `packaging.yaml` hold a block; an error when any of the three disagree (`oerconfig.project_conflicts`; `docs/configuration.md`, "Where the book is named").

### Sidecars and reports

**Reports live in the book's directory; a sidecar's place there is only a default.** In v0.1 the book's directory was also where the scripts were, because the scripts were copied in. They aren't now, and keeping reports beside the tools would mean two books overwriting each other's corrections. Reports are written by the run and regenerated every time, so they belong beside the book. Sidecars have the opposite lifecycle: they're read, never written, and hold the only thing in the pipeline no script can reproduce. The book's directory is the one you delete to rebuild and the one replaced wholesale when the publisher reissues the source, which makes it the wrong permanent home. So `sidecars.table_captions` and `sidecars.image_alt` take an absolute path, or one relative to the book's directory, and corrections can live somewhere version-controlled. The v0.2 changelog first covered reports and sidecars in one sentence, which is what made this ambiguous; they need separate entries.

**A sidecar holds a judgment the source file doesn't.** Whether a first column labels its rows, whether a link's text conveys its purpose: neither is in a Word file under any reading. So no upstream change that has Pandoc read more of a Word file, its properties in `docProps/core.xml` ([#3034](https://github.com/jgm/pandoc/issues/3034)) or a hyperlink's ScreenTip ([#11869](https://github.com/jgm/pandoc/issues/11869)), would remove a sidecar.

**A sidecar can gain a column without breaking the ones in circulation.** `read_sidecar` zips the header names it knows against each row, so a column it doesn't recognize is ignored and a row missing one reads as empty. Verified by appending a `reviewed` column to a real `table-headers.csv` and running the pre-pass, which read the file unchanged (by 0.8, 2026-10-03). That is what makes it reasonable to defer a decision about a sidecar's format rather than adding a field speculatively because changing the format later looks expensive. It isn't expensive; the cost is in the tools that would have to fill it.

**A sidecar a person fills in ends with two columns, `Drafted by` and `Reviewed`** (2026-10-03), shaped for a later step in which a standard LLM API drafts alt text, table descriptions, and perhaps table headers (on the roadmap, after 1.0). Two columns, not one, so that a reviewed value keeps who drafted it, for an institution's record of AI-assisted, human-reviewed text, and to measure how often drafts are kept as they are. A drafted value is used whether or not it's reviewed, as the table-header guesses always were. The names aren't `Source`, because `Source` is already a column in two reports (the source page). The readers read by position and ignore extra columns, so the two go last and an old sidecar reads as before, as a person's; `REVIEW_COLUMNS` in `convert.py` names each sidecar's value and review positions. Left out: `page-names.csv` and `math-keep.csv`, which hold no judgments a model would draft (`docs/sidecars.md`).

**A CSV a run writes for a person guards a cell a spreadsheet would take for a formula, now, not only in a front end** (2026-11-12). The cell gets an apostrophe before it, OWASP's advice, and a cell that begins with apostrophes before such a character one more, so every reader can take one off and read what was written: `lib/sidecars.py`'s `csv_writer`, `csv_rows`, and `dict_rows`, and `figures-and-tables.lua`'s own reader. The case for doing it everywhere is that a book's text reaches the cells (alt text, captions, a formula's TeX, a link's words) and a person opens them in Excel, so a book could carry a formula into someone's spreadsheet; the cost is the apostrophe a person sees, and a script that reads a report with Python's `csv` module finds. In the CSVs the runs here had written, 53 of 117,314 cells began so, in two reports (_Instrumental Analysis_'s `math-repaired.csv` and _Introductory Business Statistics 2e_'s `cnx-table-summaries.csv`), none in a sidecar (counted 2026-11-12). OWASP's other remedy, a tab inside the quotes, was left: it stays in the value, and the tools read their own files. Not tried in Excel.

**A sidecar the run rewrites is flushed to the disk before the new file is moved into the old one's place**, which a crash on XFS could otherwise leave empty (checked by counting the flushes, 2026-10-26; `lib/sidecars.py`'s `_replace`).

## Tables

### Headers, bands, and titles

**`row_head_columns` is how a table's header column is declared, and the filter adds `scope` itself.** Setting it from a filter works and Pandoc's HTML writer honors it, emitting a bare `<th>`, so the filter adds `scope`; both survive to EPUB3 and are byte-identical on Pandoc 3.1.3, 3.9, and 3.11, so the mechanism doesn't turn on the Pandoc version (measured by 0.8, 2026-10-03). What did depend on the version: `<w:tblHeader w:val="0"/>` read as a header row until 3.10, and none of the 1,011 files in the four OpenStax books measured carries one (PANDOC-NOTES, The DOCX reader and The HTML writer).

**The sidecar outranks a page's own `<th>`, which outranks the guess**, the same order as for Word. The header pre-pass writes the value in effect into an HTML table's marker rather than matching positions afterward, and runs once after every source is read, so the book has one report and one new-rows file. A table no cell of which could be a header is `needs-source`, and its note says where the headers go: in Word, or as `<th>` cells in the page. The status was `needs-word` until HTML tables reached the pre-pass.

**A declaration's row numbers mean the same rows in the pre-pass and the filter.** The filter's row counter skipped a table body's own head rows and the foot, which no Word table has, so on an HTML table grouped by `<tbody>` the declared rows landed on the wrong rows and the first group vanished. Both count head, then each body's head and rows, then foot. And one header row above the first band, unmarked, heads every part; it had become a part of its own, for Word tables as well.

**A banded table is interpreted once and expressed per target.** A title row folds into the caption everywhere. Bands, whether inferred from merged rows or grouped by the source's own `<tbody>`, are split into a table per band for HTML, EPUB, and PDF (`tables.bands: split`) and kept as one table with a body per band for Markdown, AsciiDoc, and DOCX (`group`), whose output becomes a source and reads back as written; `auto`, the default, chooses by the target's format. The split is what NVDA handles fully: tested by Rob in Chrome and Firefox, it reads a part's caption on arrival. The split happens in each target's own intermediate rather than at render time, reusing the machinery that already gives targets differing in a filter-stage setting their own intermediates; the cost is a second filter run per page when a book has both kinds of target. If JAWS or VoiceOver announce row groups, HTML can switch to `group` with no change to what the book says; neither has been tried. A third form for HTML, the bands as a column of their own spanning their rows, was a candidate at 0.8 and is the setting's `column` now, never the default (`bin/schema-conversion.yaml`).

**A merged first row over a header row is the table's title only where that header row heads every group** (`tablecensus.heads_every_group`, since 2026-10-13): every row's cells are where the header row's are, and no band below has a header row of its own, one repeating half its words or more, or one reading as a header row over the rest of its rows (bold or shaded where they aren't all, or words over numbers). Otherwise the merged row is the first band, and the split takes it and the head's rows after it out of the head for the first part. The rule it replaced made a band in the head over a header row the title whatever was below, which got _Clinical Nursing Skills_' Table 12.2 wrong: two tables in one, its second part headed by the first's header row over its own.

### The header guess

**One function, `guess_table`, guesses for the census, the Word path, and the HTML path, so what the census says is what a conversion does.** The per-part guess of a banded table lived in the header pre-pass's Word path only, so the census and HTML tables guessed a banded table whole, which usually says `none`: _Economics_' Table 7.14 was `none` in the census and `both` in the conversion. The parts' vote had three faults besides: it shared only the rows Word marks to repeat, where Pandoc also reads row 1 as the head under Word's first-row flag, so _Business Communication_'s Table 22.6 came out of a Word conversion with its header row as plain cells in every part; a part too small to judge voted `none`; and a tie went to whichever value a Python set yielded first, which string hashing randomizes per process (`lib/tablecensus.py`; by 0.8, 2026-10-03).

**The census reads a table through a view, not the OOXML.** `classify()` and `explain()` read four things: the grid, Word's table-look flags, the style name, and the rows marked to repeat as a header. A `View` holds them, built from OOXML or from Pandoc's AST (`view_from_pandoc`), so the same rules guess an HTML table's headers. Every census and pre-pass check passed unchanged after the refactor. On the Information Systems book, 35 of the guesses were `first-column` on term-and-definition tables; all 35 had a bold first column, so that was Word's rule applied faithfully, not a new one.

**`classify()` returns one kind, and a table can be several things at once**: a merged title _and_ a header row _and_ a header column, all in `BC-07.docx`. Anything consuming `kind` as the whole story drops findings, and the dropped finding stays visible in the evidence string, which is why it survives review: the output looks complete. So the guess asks the individual questions and uses `kind` only where it's decisive.

**A numeric first column needs an ordering test, not a numeric test.** The question is whether the first column labels its rows, and `Year | GDP | Deflator` and `Group A | Group B | Group C` can't be told apart by type: both are unique, both sit over a numeric body. What separates them is that a lookup axis is sorted and a data series isn't. 110 tables of the corpus turn on this, and they split 78 to 32. The residual error after it is about two tables in 332, where a three-row data column happens to ascend (by 0.8, 2026-10-03).

**`mostly_numeric` passes a small column on less than 60 percent, on purpose.** It uses `int(0.6 * n)`, which truncates: one number in three cells passes, two in four, four in seven. It feeds five decisions, among them whether a first column keys its rows and whether a body counts as numeric, and it decides whether a bin column (`1`, `2`, `3-4`, `5+`) reaches the ordering test at all. Measured on the whole corpus, an exact 60 percent changes one guess of 1,045, and changes it from right to wrong: each part of a banded database table has "1 | John Doe | 123 Main St" under its header row, and only the loose threshold lets the words-over-numbers rule see that header. So it stays loose, with the measurement beside it in the code. The first measurement said it changed nothing, because the census then guessed banded tables whole: a rule can behave differently on the small parts of a banded table than on whole ones, so what's measured has to be what the pipeline does (by 0.8, 2026-10-03).

**`none` is a claim about the table and needs evidence; a table no rule recognizes is `unknown`.** Two fallbacks of the guess returned `none` with no evidence of a plain grid, "too small to read, and nothing marks a header" and "no header row, no header column, and no keying first column", which means no rule recognized anything; and `none` goes into the sidecar's prefilled row as though someone had decided it. In _Introductory Business Statistics_ all 17 `none` guesses came from the second fallback and were right (grids of raw observations); the risk is headers in a shape the rules don't know, like the payoff matrices, which also came out `none`. So the fallbacks give `none` only when every filled cell is a number or an amount, or the table is a list laid out in columns (short terms in alphabetical order down each column), and `unknown` otherwise, which is a claim about the guess rather than the table. A table whose header band sits below row 1 gets `unknown` too, and the sidecar accepts `manual` and `list` for a person's by-hand cases. First, two shapes that accounted for most of the `none` guesses got rules of their own: a two-column box of labeled fields is `first-column`, and a title row over an unmarked row of short labels is `first-row`. Across the corpus that moved 39 tables from `none` to a value and 19 to `unknown`; 17 stay `none` (twelve grids of amounts, five keyword lists). The 20 `unknown`s are the tables a person should see: payoff matrices, sideways tables, formula glossaries, label columns too long to be labels (by 0.8, 2026-10-03; `docs/sidecars.md`).

**The header guess takes a number signed with a minus sign (U+2212) for a number, and not one signed with an en dash** (2026-10-19). `NUMERIC` in `lib/tablecensus.py`, the pattern a cell must match to be a number, took a hyphen for a negative's sign and not the minus sign, which OpenStax's books write one with, as `QUANTITY` and `AMOUNT` already did; `parse_number` reads the sign, so a column of such numbers is ordered by it. Measured with the census on the Word corpus's seven books (2,943 tables), no guess changes, with an en dash taken too or not; on the 67 books then unpacked from OpenStax's CNXML (12,221 tables), one: _Contemporary Mathematics_' 3.2, a table of numbers (−3, 24, 36/4, …, −16.0) beside whether each is an integer, whose first column the guess took for labels (`first-column`), two of its numbers being words to it, and takes for numbers now (`unknown`). The first guess is the one a person would make, but it was made for a reason that was wrong. **A table's notes on its rows are no bands, and leave it no header column** (2026-10-22). Three tests of a sentence's form (no parentheses round it, three words or more, and not in title case) changed none of the 15,935, so the rule hasn't them.

**`is_full_width_band` is true for every row of a one-column table, so a rule that reads past such rows needs a guard for it.** That one fact produced three separate defects: the title-row scan consumed whole tables, the header-row test refused to look at a bold row 1, and the words-over-numbers test was handed an empty row list. **`build_grid` repeats one `Cell` object across the width of a merge, so a printed grid reads like repeated text.** One Word file of the corpus, an appendix reviewing Python functions, looked in `build_grid`'s output as though it wrote its grouping bands as repeated text rather than merged cells, which the census couldn't then have seen. The general form: when a data structure normalizes the thing being observed, the observation has to go under the normalization.

**A sample case's predicate tests the table's own property, not the guess, and the sample document is regenerated after every change to the rules.** Three of the sample generator's cases inferred a property from the guess and matched the wrong tables: `single-column` matched image-only layout tables, `stacked-column-headers` matched merged title rows, and `numeric-first-column-unordered` never tested for disorder at all. Every one of these, and of the one-column table's and `classify()`'s above, was found by a person reading an example; the suites passed throughout, because each was a case where the code did what it said and what it said was incomplete.

### Data grids and layout tables

**A data grid with no relationships to encode is left a plain table, with a caption.** The statistics book's `5-practice.docx` has 28 measurements laid out four rows by seven columns to fit the page. Row 2 is not a thing, column 4 is not a thing, and the reading order is prose order. WCAG 1.3.1 has nothing to require of it because there is no relationship to encode, so it conforms by being left alone: no `th` anywhere, all `td`, and a `<caption>` so that someone browsing in table mode can identify it. The caption is the part that matters and the part the source usually lacks: a grid of bare numbers with no caption is unidentifiable in table mode, and the surrounding prose normally already says what it is. The further step is a recommendation to the author rather than a conversion: 28 numbers with no relational structure are a list, and W3C makes the same move for long descriptions, pushing content into prose where markup can't carry it. Its place is a note in the report beside a `none` declaration, not something the run does silently.

**A data grid is not a layout table, and isn't marked as one to silence a checker.** Word's Accessibility Checker flags a table with no header row and offers "Mark as layout table" as a fix. Taking that offer is a false declaration: a layout table positions content, and this one presents data. A layout table's `role="presentation"` tells assistive technology to ignore the grid's structure entirely, which is strictly worse than the conformant do-nothing. Since 2026-10-19 `table-headers.csv` takes `layout`, and the pages and the EPUB give such a table that role (`docs/sidecars.md`); the value is for a table that only lines things up, and a data grid stays `none`.

**A layout table keeps its place among its page's tables.** The filter counts a layout table in its page's position keys (`steps#table-1`), so a change that stopped counting it would move the key of every table after it on the page, and the sidecar rows keyed on them (noted with `main` at a494d8b, 2026-10-15; `figures-and-tables.lua` still counts one).

## Math

### Math in a source

**`math.from_text` and the equation repairs are conservative because of what a prototype measured** (2026-09-27). The questions were whether odd characters used for math can be remediated automatically, and whether text meant as an equation can be detected and rewritten as math. A prototype, not in the repository, ran on Pandoc's AST, where math typed as text is italic single letters, Greek, digits, sub- and superscripts, and relations or operators. It found 2,103 expressions in the statistics book (`H_a: σ^2 > 5^2`, `y = –0.125 – 3.5x`, `Z ~ N(0, 1)`, `P(x ≤ 160)`), and in two random samples of 22 every one was math, but about a quarter were fragments cut at an edge (`A =` before a set in braces, `df =` before a blank, `= P`), which would split an equation between math and text. Across 771 other files (all of _Economics 3e_ and _Principles of Data Science_, 60 each of four others): 13 expressions, among them nursing's dosage formulas (`Hx = DQ`) and one false positive, a year range `1773–1799`. Lone symbols (an italic letter or a Greek letter alone in prose) are 2,109 in the statistics book and mostly variables, but elsewhere mostly italic letters in references and emphasis (`U`, `S` from an italicized "U.S."), so not safe to convert automatically, except perhaps Greek letters and letters with a subscript. Inside the statistics book's 2,396 equations: x̄ written as `\overset{¯}{x}` 233 times and as `\overset{–}{X}` 205 times, the en dash as minus about 70 times, µ for μ 44, ∆ (increment) for Δ 14, ŷ precomposed 10, and `H_{Ø}` for the null hypothesis once. Those are mechanical to normalize, and normalizing them would also clear the 54 characters then missing from the book's PDF (`docs/configuration.md` has the rules as built and the later counts).

**A letter with a hat or a bar typed as text is made math only where it is math, and text that isn't math isn't normalized** (2026-10-24). The form wanted is the equation's, which a screen reader reads, but only when the character is math: NVDA doesn't read the typed forms correctly, and in a sample whose words with a circumflex were changed too it read "hat" where the English words were meant (Rob, 2026-10-24). The decks in question type an equation as if it were ordinary text, so the change is the narrower one, in what `math.from_text` takes for an equation (`math-repair.lua`, `accented_at`, `pieces`): a letter followed by a combining circumflex, macron, or overline (U+0302, U+0304, U+0305), or a precomposed `ŷ`, standing alone, is a variable; a script after it typed as TeX types one (`x̄_n`, `^2`) is its script; and in a run holding one, a plain letter or two after an operator, a relation, or a number's digits, and before an operator, a relation, or the run's end, is a variable too, so `ŷ = a + bx` and `ŷ = 2x + 1` are equations, where `a + b = c` stays text. A letter with a hat in a word (`crêpe`) is the word's. On OpenStax's 13 decks the two expressions in the notes of decks 13 and 7 change, `\hat{y}=a+bx` and `\bar{x}_{n}`, and nothing else.

**A formula in running text that its page sets in display style is set so only where `math.display_style_in_text` says, and that's off by default** (2026-10-27). The setting is the run's, not the CNX unpacker's, because the question is general: Pandoc's HTML reader drops MathML's display style, an `mstyle` with `displaystyle="true"` or a `math` element's own, on any HTML page (PANDOC-NOTES, The HTML reader). Such a formula is marked at reading, whatever the setting, which keeps one reading for every target, since the reading stage's environment has no target's settings. `math-repair.lua`, a filter-stage filter, then sets each marked formula in display style after its repairs, so that its TeX is the same to `math-repaired.csv` and `math-keep.csv` whatever the setting, `\displaystyle` opening it, where the target's `math.display_style_in_text` is true (`MATH_DISPLAY_STYLE_IN_TEXT`, a filter setting, so targets that differ get intermediates of their own), as `html-source.lua` sets a formula of the class `displaystyle`; a page's and an EPUB's MathML then carry it as an `mstyle` (`target-blocks.lua`), and a Word file doesn't; and either way the filter takes the marking span away where it holds nothing else. Measured on _Calculus Volume 2_'s third chapter, a target with the setting beside one without: 551 formulas kept in display style, on 10 of its 12 pages, as the run says, and its PDF 132 pages, where it's 121 without (the two built in 902 seconds, the pages read once).

**A unit of two letters that nothing marks stays italic letters** (2026-10-19). An identifier of two letters is made text only where its source sets it upright or applies it as a function. Of the 988 identifiers of two letters in OpenStax's public repositories that are neither, most are products (`πr` 35, `rω` 35, `ρv` 33, `mc` 31 in _College Physics_), and some are units: _Contemporary Mathematics_' `cm` 65, `dm` 21, `km` 20, `mm` 15, `mL` 12, and `kg` 10, the nursing books' `mg` 39, `mL` 28, `kg` 16, and `lb` 8, and _Mikroekonomia_'s `zł` 7. A list of units would set most of those right, but not without a product written like one: _College Physics_' `w = mg` (m times g, 3 of the 55 `mg`) and `Q = mLf` (3 of the 43 `mL`). So there's no list of units; no better compromise was found.

### A bar and a hat in Office math

**A bar over a letter is an accent of the macron (U+00AF) in a Word file and in a `pptx` target's deck; a PowerPoint deck's remediated copy keeps a bar typed as an upper limit, a macron in place of an en dash.** Six forms of X̄ were tried in Word and in PowerPoint (tested by Rob with Narrator and NVDA, 2026-10-10): A, a macron typed in an upper limit, as OpenStax's decks have it; B, an accent of U+203E, as Pandoc writes `\bar` and as the repair had written it since 0.8; C, an accent of U+0305; D, of U+0304; E, of U+00AF; and F, Office's overbar structure, as PowerPoint itself writes a bar and Pandoc writes `\overline`. B is silent in Narrator in both programs. For a Word file F was chosen first, as what PowerPoint itself wrote and a form both Narrator and MathCAT read (E would have served as well; C fails MathCAT), and then E, the same day, because it matches the meaning: x̄ is an accent, which TeX writes `\bar` and keeps apart from `\overline`'s line over an expression, and Office's own UnicodeMath gives `\bar` as an accent of U+0304 ([UTN #28](https://www.unicode.org/notes/tn28/UTN28-PlainTextMath-v3.2.pdf), 3.10), where F is Office's `\overline` (Microsoft's list gives U+00AF for `\overbar`, `\overline`, and `\vinculum`, "Repeating decimal"). Of the forms both screen readers read in Word, E is the accent, and Narrator reads it letter first. E was taken for a remediated copy and for the `docx` target on condition that it be safe downstream, and it needed one thing there: Pandoc reads E back as `\overline`, so `docxrepair.bar_accents` gives an accent of the macron the overline again as a Word file is read, and the file reads back as `\bar` (`docxremediate.BAR`, `docxtarget.bar_accents`). A deck's remediated copy leaves the bar as typed, a dash there made a macron: in PowerPoint NVDA reads an equation's characters alone, and A is the one form both screen readers read there (`remediate_equations(..., macron_bars=True)`). On OpenStax's decks 2 of the 73 equations change, each an en dash made a macron (the other 11 bars are macrons already), and each changed deck differs from its original by that one character. The `pptx` target's bar is E, as Word's (2026-10-12): NVDA read the target's form A as "x" in Slide Show (Rob, 2026-10-12), so A gained nothing there and consistency with Word decided it.

**A hat over a letter is an accent of U+0302, in Word files and decks alike.** Three forms of ŷ were tried (tested by Rob, 2026-10-11): A, ŷ typed as one character (U+0177), as the statistics textbook's Word files have it; B, an accent of U+0302, Pandoc's `\hat` and the repair's; and C, an accent of U+005E, LibreOffice's. B is the only form any screen reader read as "y hat" (Narrator in both programs, MathCAT in Word), and is Office's own hat; C loses the hat for Narrator, which takes ^ for a power, and A loses it everywhere. NVDA in PowerPoint reads no hat in any form, so unlike the bar, whose typed macron it reads, a deck has nothing to gain by keeping ŷ as typed, and the repair makes it B there too.

## Images and media

### Paths and names

**Never assume a path the filter sees is the path on disk.** In the two-step conversion `convert.py` performs, the filter already sees `media-a/media/image1.png`, because `--extract-media` rewrote the paths in step 1. Converting a `.docx` straight to HTML in a single pass, it sees `media/image1.png`. `qualify_media()` and `source_stem()` matter only for the filter run on its own, as `docs/architecture.md` documents it; `tests/run-filter-tests.py` has a `single_pass` case that reaches them.

**A `markdown` target's media keep the author's names.** Every other target copies media under names that need no encoding in a link; a `markdown` target writes source, whose references are the author's, so its copies keep the author's names, or the written Markdown refers to files that aren't there (14 unresolved on the economics book before this was fixed). `media.lowercase`, below, is the one setting that changes them.

**`media.lowercase` changes names in the output alone, and nothing in the author's tree is renamed** (decided 2026-10-09, built 2026-10-15). Lowercase with forward slashes is safe as a normalization, with five things to handle: two files whose names differ only in case collide, and the run has to stop; external addresses aren't lowercased (only the path of a local reference); every reference has to be rewritten, in every source and sidecar key that names the file; a backslash is a separator only in the reference's parsed path, not its text, since Pandoc's Markdown takes a backslash before punctuation as an escape; and on macOS and Windows, whose file systems ignore case, renaming `Foo.png` to `foo.png` in the author's own tree takes two steps (through a temporary name). In a copy there's nothing to rename in place, so the setting is for the output: an `html`, `revealjs`, `markdown`, or `asciidoc` target's copies take lowercase names and its pages name them so, and a `source` target's copies keep the author's names, which name the author's files. For a PowerPoint deck a picture's name doesn't matter at all once the deck is a zip; the option is for Markdown decks and books, where sample deck S06's six mis-cased names are the test.

### Frames and remote images

**A frame stays a frame in HTML and is a link in the EPUB; a remote image the same.** An EPUB holds its own resources, and a reading system won't fetch. The link is named by the frame's title or the image's alt text. A frame keeps pointing at what it shows: a browser's recording of a site held each YouTube player, and the site unpacker first rewrote 25 frames to local copies of the player, against this decision. In an EPUB a YouTube or Vimeo frame links to the video's own page, since the embed address alone shows "Video unavailable".

**`[html-raw] … iframe x1` in a run's messages counts the closing `</iframe>` fragment**, the frame itself having been made an embed. It's misleading to read but deliberate, and tested as such (the convert suite's `"iframe x1" in marked.stderr`; seen converting OpenStax's books from CNXML, 2026-10-14).

### `images.downsample`

**`images.downsample` measures an image against the width its page shows it at, and makes its copies once per value** (2026-10-18). The width an image is shown at is its page's, in CSS pixels, from its `width` or its `height` and proportions, no wider than the column (36em, 576 pixels at a browser's default size); `images.responsive` drops a height, so an image sized by its height alone measures at its own width, which the convert suite's case had to turn off to test. Copies are made once per value, in the run's temporary folder: an `html` or `revealjs` target copies them in the originals' place, and the EPUB, Word, PDF, and deck writers find them first through `--resource-path`, which puts its folders before `.` (PANDOC-NOTES, Options every writer shares). The source-like targets, and a LaTeX book's PDF from its own files, keep the originals. Without Pillow a run that sets it stops before reading a page. On _Instrumental Analysis_ as first built: at 0 the run warns of 442 images, 173 over twice their shown width, up to 11.9 times (`nmr_tube.png`, 2,150 pixels shown at 180), 143.2 MB; at 4 it scaled 31, 83.1 MB to 33.1 MB, and the EPUB went from 142 MB to 93, the Word zip from 155 to 102, and the PDF from 165 to 112.

**A copy that comes out larger than its original isn't used, and trying a larger multiple never helps it.** As first built, at 4, 42 of the 73 images over the ratio were kept whole: 40 drawings, whose flat colors compress better than a smaller copy's smoothed edges, and 2 photographs under 5.5 times. Using the larger copy anyway is the strict alternative, and wasn't taken. Trying larger multiples, up to the original's size, until one compresses was studied and not built (2026-10-19): every image a run keeps whole was copied again at each whole multiple from the setting up to the original's width with `downsample.scale_one`, as a run copies it. At 4, 42 kept, and not one copy at 5, 6, or more came out smaller than its original; at 2, 77 kept, and none at 3 or more. For every one of them the copy grows with the multiple, more pixels and more bytes. Why they're kept at all: the originals are drawings in RGB or RGBA PNG with few colors (most under 500; 49 to 6,705 at 4), which PNG compresses well, and a resampled copy's smoothed edges hold thousands of colors in between, which it compresses worse, whatever the copy's size. The 77 at 2 are 64 RGB and 13 RGBA PNGs, none a JPEG.

**What does make a drawing's copy smaller is a palette, and a palette is for drawings only.** Quantizing a copy to a palette was tried first and rejected, since it bands gradients (Figure 10.3 at 43 dB); that rejection was of photographs and gradients too. Measured on the images of the study above (2026-10-19), quantizing the copy to an adaptive palette of 256 colors (median cut, or fast octree with transparency, no dithering): at 2, all 77 kept copies come out smaller than their originals, 4.9 MB to 2.7, and the 58 drawings' copies the run already made (originals of 4,096 colors or fewer) shrink 5.4 MB to 1.5, 6.2 MB in all of about 48 MB of images; PSNR against the unquantized copy is 42.5 dB at worst (Figure 12.19, 934 colors), where a 3× zoom showed no difference. Mapping a copy to its original's own colors instead, where it has 256 or fewer and no transparency, worked for 48 of the 77, 2.7 MB to 1.1. The 26 photographs among the PNG copies (originals of more than 65,536 colors, 18.9 MB of copies) would shrink to 4.0 MB with a palette, at 32.9 to 41.9 dB, and the worst, `slits.png`, showed speckle in its dark background at 3×.

**The palette as built** (`lib/downsample.py`, 2026-10-19). A PNG copy whose original is in RGB or RGBA and has 4,096 colors or fewer (`drawing`, `DRAWING_COLORS`, `getcolors` stopping at the limit) is quantized to an adaptive palette of 256 (`PALETTE_COLORS`): median cut, or fast octree for a copy with transparency, which median cut refuses; Pillow's quantizing to an adaptive palette doesn't dither, whatever `dither` says (read in `Image.quantize`, 12.3: dither applies only to quantizing to a given palette). An RGB original's transparent color (its `tRNS` chunk) is made an alpha channel first: Pillow keeps it on the quantized copy as a color, which its PNG writer can't write for a palette image (a `TypeError` on Pillow 9.0 and 10.2, Ubuntu 22.04's and 24.04's, which stopped the run; a `ValueError` on 12.3, which kept the image whole). An image in shades of gray gets no palette; _Instrumental Analysis_ has none (its 468 PNGs are 289 RGBA and 179 RGB, none with a transparent color). A copy only exists where `images.downsample` scales, so nothing else changes; a copy still larger than its original is kept, as before. The run's line counts them: "images.downsample 2: 173 of 483 image(s) scaled down to 2 times the width they're shown at, 130.3 MB to 26.7 MB, 135 of them drawings given a palette of 256 colors." So at 2 every image over the limit is scaled, where 77 had been kept; the 77's copies are 4.9 MB of originals down to 2.7, and the 58 drawings already scaled went from 5.4 MB of copies to 1.5, 6.2 MB in all, as the study measured. Against the same copies in full color, the worst is 42.5 dB (PSNR; Figure 11.8 and Figure 12.19), and the 48 with transparency keep it to 48.2 dB or better; a palette's opaque colors can average an edge's alpha in, so an opaque area can come out at 254 where the original is 255 (the convert suite's drawing; its check allows it). At 4: 65 of 73 scaled, 89.2 MB to 34.0 MB, 45 of them drawings, and 8 kept: `cobalt_complexes.png` and `xy_recorder.png` (photographs, 102,911 and 51,934 colors), `icp_ms_instrument.png` (a diagram of 6,705 colors, over the limit), and five drawings 4.05 to 4.97 times as wide as they're shown, whose copies have nearly as many pixels as they do. Tested in the convert suite's downsample case (a drawing of eight colors, one with half of it clear, one with half of it in a transparent color, and a photograph of noise), each check failing in four ways of breaking it (no palette; the limit raised so photographs take one; median cut for transparency, which stops the run; the transparent color left a color, which stops the run on Pillow 10.2 and keeps the drawing whole on 12.3).

### `images.compress`

**`images.compress` sets the highest quality a JPEG keeps as well as a limit on its pixels, because the waste in a book's images was its JPEGs' quality** (measured on _Principles of Marketing_, 2026-11-04). OpenStax saved 87 of the book's 110 JPEGs at quality 99, the most JPEG has but 100, and 21, the chapter openers, at 94 (each JPEG's quality as ImageMagick reports it, and as `jpeg_quality` reads it from the file's luminance table, the same for 109 and one less for the other), all at full color resolution (4:4:4). Written again at their own size, as the run writes them, the 110 are 22.9 MB at quality 90 keeping their color's resolution, 18.0 at half of it (4:2:0, libjpeg's default), and 14.3 at 85 (written with the run's own `scale_one`; an earlier count, which didn't write them quite as the run does, had 22.2, 17.3, and 13.6), where scaling every image to twice the width it's shown at, at quality 90, as `images.downsample: 2` does, leaves 49.4 MB of the 59.6, since most of the photographs are no more than 1.4 times as wide as they're shown. So each of the three levels is a limit, as `images.downsample`'s, and a quality: `print` 4 times and 90, keeping the JPEG's color resolution, `screen` 2 times and 85, and `small` 1 time and 75 (`docs/configuration.md` has their sizes). The JPEGs written again, against their originals: at quality 90, 36.0 dB (PSNR) at the median and 28.3 at worst, MKT_Figure_16_02_006, a photograph of colored words on a textured board, 35.1 when it keeps its color's resolution, as `print` does; at 85 with half the color, 34.9 and 27.7; at 75, 33.5 and 26.6. A crop of that photograph at twice its size, side by side at each, showed no difference but a little softness at colored letters' edges at half the color's resolution; and a chapter opener's page rendered at 200 dots an inch, whole and at `screen`, looked the same.

**A JPEG copy's EXIF resolution is scaled with its pixels, as its header's is** (`_exif_for_copy`, 2026-11-04). 89 of _Marketing_'s 110 JPEGs record their resolution in their EXIF data alone, which Pillow reads as an `IFDRational`, a number but not a `float`, so `scale_one`'s check passed over it and wrote the copy's JFIF header without one; and the copy kept the original's EXIF data, 200 pixels an inch, which LuaTeX and Pandoc's Word writer read before the header: a JPEG whose header says 144 pixels an inch and whose EXIF data says 200 is drawn at 200 by LuaTeX in TeX Live 2026 and by Pandoc 3.12.1 and 3.13 in a Word file, so a photograph 800 pixels wide, drawn 4 inches wide, was drawn 2.88 inches wide at `small`, its copy 576 pixels wide (LATEX-NOTES and PANDOC-NOTES have the two readers). `images.downsample` had done the same since it was made, unseen, its measurements having been of bytes.

**There's no gray level.** On top of a level, _Marketing_'s images in shades of gray would be 43 percent smaller at `print` (34.6 MB to 19.8, `print` keeping the color's resolution), 25 percent at `screen` (18.1 to 13.5), and 13 percent at `small` (6.6 to 5.8), their files' bytes (measured again after the resolution fix above, which made `small`'s copies 0.5 MB smaller, and `screen`'s and `print`'s no smaller at a tenth of one), and the PDF, nearly all images, about as many megabytes smaller, roughly 41, 19, and 6 percent of it (2026-11-04). That's less than the levels themselves save, and it takes away what color says, a chart's series or a map's regions, which a book's text and a reader's eye go by (WCAG's 1.4.1 asks that color not be the only way something is said, which a book's figures don't always meet). A reader who prints in black and white gets gray from the printer.

### A caption that repeats its picture's alt text

**A figure's caption that says what its picture's alt text says is hidden from a screen reader in its words, not its notes' marks, and one with a link of the author's is shown whole** (2026-11-09). Where a Markdown picture's description is its caption, as an implicit figure's is, Pandoc's HTML writer hides the caption from a screen reader (`aria-hidden="true"` on the `figcaption`), so its words are read once, as the picture's alt text (PANDOC-NOTES, The HTML writer). It leaves a note out of the comparison, so a caption with a note was hidden with the note's mark, a link that can't then be reached from the figure, which axe-core's `aria-hidden-focus` reports: measured on c364e2a, `<figcaption aria-hidden="true">A gray circle<a … role="doc-noteref"><sup>5</sup></a><a …><sup>6</sup></a></figcaption>`. Where the caption held a formula too, `target-blocks.lua`'s own hiding (since 2026-11-07) left a caption with a note shown, the words read twice and the mark reachable. Three ways were weighed: as it was, hidden or not by whether a formula is there; every such caption shown, the words read twice; or the caption's words hidden in a span and its marks not, the words read once and each mark after them, a link to its note. The third was taken. Giving the picture its alt text as an attribute, the first idea for keeping the writer from hiding the whole caption, wouldn't have kept it: the writer compares the caption's text with the `alt` attribute where the picture has one (`captionIsAlt`, read at 3.9, 3.12.1, and 3.13), and a caption whose words, its notes left out, are the attribute's is hidden still (measured with 3.13: `![A gray circle[^1]](c.png){alt="A gray circle"}` gives `<figcaption aria-hidden="true">`). The writer compares only a figure whose one block is a `Plain` holding the picture alone, so `hidden_caption` puts an empty `Str` beside the picture, which the writer writes as nothing, the `img` as before, and hides the words itself: `hidden_words` puts each run of the caption's words in a span (`aria-hidden="true"`) and leaves each note, one in emphasis or in another inline that holds words among them, with the words around it hidden. So too with a formula in the caption, which the span had left shown, the words twice, and beside an EPUB's link for a picture on another server. A caption with a link of the author's had the same problem as one with a note, and there the answer is not to hide it: `hidden_caption` looks for a link in the caption before it leaves a caption with no formula and no note to the writer, and a caption with one that says what its picture's alt text says is shown whole, its words read twice, with the empty `Str` beside the picture, as for a caption with a note, and no span. So with a note in it too, link and mark both reachable; and beside an EPUB's link for a picture on another server, which the writer hides no caption beside, as before. The PDF keeps both, a caption and the figure's description, as PDF/UA-2 wants.

## Links, ids, and titles

### Files, names, and links

**A page's name is its source's name made safe for an href.** Percent-encoding the manifest's hrefs was correct by the IMS specification and not enough. So spaces and other URI-special characters are replaced in the page's name and in the names of media copied beside it, by one rule in `lib/names.py` and `safe-media.lua`, which must agree (ASCII letters, digits, `.`, `_`, `-`, and the slash; runs of anything else become one hyphen; no hyphen before an extension). A hand-written page keeps its name, with a warning, because its own links are the author's. Two files that the rule would give one name stop the run: two sources (`ch1.md` and `ch1.adoc`, `Chapter 1.docx` and `Chapter-1.html`) before anything is read, two images (`a b.png` and `a-b.png`) at the media gate.

**A file a page links to is carried into a target as an image is; an EPUB can't carry one, and keeps the link's text.** Images were carried, through the media copy; a PDF or Word file a page links to wasn't, and no book before the Common Cartridge exports had local links of that kind. Course pages do, and the packager stopped on them as missing. The safe-name filter renames a link to a local file as it does an image, and the copy step copies it; the media gate still checks only images, since a link to a missing file never stopped a run and shouldn't start now. An EPUB can't carry such a file at all: Pandoc's writer embeds images but leaves other links as written (`transformInline` in `Writers/EPUB.hs` touches only `Image`), and a reading system follows links only among content documents, so `target-blocks.lua` keeps the link's text without the link and the output check reports the file (`link-to-file-dropped`). OpenStax's cartridge built as an EPUB went from five RSC-007 and one RSC-005 (an `aria-controls` on one of those links) to none, confirmed by running epubcheck directly after the report showed no epubcheck rows at all (by 0.8, 2026-10-03).

**Publisher links are rewritten on the filtered intermediates, before the split**, so the split and the assembler treat them as any link between pages: `…/books/<book>/pages/<page>#anchor` becomes `<page>.html#anchor` when the book has the page (`links.rewrite_publisher`, default on).

### Ids

**Every id on a page is unique, as the filter's last step.** OpenStax names a bookmark for a repeated heading the way Pandoc numbers an auto id, so the reader's next candidate for the second heading was a name already taken (PANDOC-NOTES, The DOCX reader, has the mechanism). The later element is renumbered; Pandoc walks every inline before any block, so an anchor keeps the name another file may link to and a heading is what moves, which is the right way round. Sixteen on the nursing book.

**Ids that collide when pages merge are renamed at merge time, not in the filter.** Two pages of a chapter each carry an anchor the export numbered per file; merged into one file (a `markdown` target's `merge: groups`), one has to move, and only at merge time is it known which links belong with which copy. The filter's own uniqueness pass still runs and finds nothing left to do. Ids inside the fenced HTML blocks the Markdown target writes for merged-cell tables collide too and are renamed by regex, since no attribute holds them.

### A page's title and its H1

**A declared title stands, the H1 never leaves the page, and the book's title comes from `project.title`** (the design of 2026-10-03). The problem was found through PDF/UA-1. The filter (`promote_h1_to_title`, whose schema default was then `always`) moved a page's only H1 into its `title` metadata and out of the body. HTML showed it again through Pandoc's title block (`<header id="title-block-header"><h1 class="title">`, without the heading's id); a book of several pages wrote each page's title back as a heading in the assembly (`add_page`); a one-page book (`add_single_page`) never did, so its PDF and EPUB lost the page's own title entirely (the EPUB showed the book's title in its place). And with `always`, a Word page with a Title paragraph and three Heading 1 sections lost its real title to its first section's heading. The design: a declared title wins (Markdown `title` or `title-meta`, a Word Title paragraph, HTML `<title>`); the H1 supplies the title only when none is declared (`if-absent`, the default for every source since); the H1 never leaves the page, the title being copied from it; the title block shows only when no level-1 heading of the page says the title; and the book's title comes from `project.title`, never from a first chapter.

**Inside the pipeline a page's title heading lives in its metadata, where everything reads it, and every output puts it back as the page's own H1.** The first attempt, leaving the H1 in every page's body, was abandoned: it broke 32 checks in four suites (the split, contents and group numbering, notes placement, the EPUB's nav and files), because the split, the contents, the numbering, and the assembly all read a page's title heading from its metadata, and the split itself makes each piece's heading its title, as the promotion makes a source's H1 its page's. So the filter, promoting the page's only H1, records it as `title-heading` (its inlines, as it said itself), `title-id` (its id), and `title-index` (how many blocks came before it). An H1 is the title heading when no title is declared, or when it says the declared title: the same text, or one inside the other (a section number before it, a site's name after it). Otherwise, under `if-absent`, the declared title stands and the H1 stays a heading of its own. `target-blocks.lua` puts the heading back for each writer (`TITLE_WRITER`): HTML gets a body `<h1 id>` and `pagetitle` for `<title>`, with no title block (unless the page has a subtitle, date, or abstract, which the title block shows); Word a Heading 1 instead of a Title paragraph, with the title put in `docProps/core.xml` by `docxtarget.finish`; Markdown and AsciiDoc a `#` heading with the title kept in their metadata. The assembly uses the heading's own text for a page's chapter heading unless the contents renames or numbers it, and a one-page book gets it too. The split marks each piece's heading its title heading, and `number_page_headings` numbers the body `h1`. "Saying the title" first compared raw text, so the statistics book's 10.2, whose Word Title has "Cohen’s" and its heading "Cohen's", showed both; the comparison folds curly and straight quotes, dashes, space, and case (2026-10-03).

**Under `if-absent` the declared title stands in every case, so an OpenStax page's `<title>` has no section number.** The one place the H1 had replaced a declared title was where one holds the other, the shorter of the two being the title: a web page's `<title>` that is the H1 plus the site's name. That's useful for cleaning up pages saved from the web, but not as the default, and never for a `format: source` copy. So an H1 that says the declared title, either way round, is still the title heading, shown once, and the declared text is the `<title>`; `shorter` is a mode of its own that takes the H1 when the declared title contains it and more; and the source writers never write a page's title (checked in `htmlremediate.py`, `mdremediate.py`, and `docxremediate.py`). The visible consequence: an OpenStax page's `<title>`, and so a browser tab and a cartridge's item names (`build-cartridge.py` takes them from `<title>`), no longer carry the section number, and `promote_h1_to_title: always` restores it. That's the default on condition that the user is told when it matters: the filter records each page whose declared title stands without the number its heading puts before it (`TITLE_NUMBERS`), and the run says so once, naming one example and `always` (2026-10-03; `docs/formats.md`, "A page's title").

**Whether an EPUB or a PDF opens with a title page is decided by the document's structure, not its number of files** (`title_page`: `auto`, `on`, or `off`; 2026-10-03). `auto` gives one to a book of more than one top-level entry, or to a one-page book with more than one level-1 heading or something before its title heading, a byline or a subtitle; without one, the PDF's title goes to `title-meta` (hyperref's /Title and `dc:title`) and the EPUB is built with `--epub-title-page=false`. The case that showed it: a programming textbook written as one Word file styles each module title Title; Pandoc reads them as plain paragraphs, and `word.headings: from-toc` makes them its 16 level-1 headings, in one file.

**A page's `<title>` loses the book's name at reading time**, when it repeats the book's own title after a separator, as a Pressbooks export titles every page. Letting a `contents` title override it was the alternative, and wasn't taken: a navigation title is often deliberately shorter than a page's.

## Footnotes

**Footnotes are rearranged after rendering, because Pandoc can't be asked to start counting at 7.** `notes.numbering` and `notes.placement` rewrite the reference text, the note's number, and the ids, in the HTML of every target and in the EPUB's chapter files; a Notes page or chapter holds the book's, a heading per group. A page's group came from the split's provenance at first, and comes from the contents tree since 2026-10-14 (below). A note that moves may take a file's only MathML with it, hence the OPF rewrite. `menu: on` is added the same way, after rendering, since the book's tree is only built once every page is written.

**Gathered notes are numbered across their group whatever `notes.numbering` says** (2026-10-13). It was a change of behavior, though the schema's description of `book` had said so ("numbered per group"): `page`, the default, would number two notes in one list 1.

**A page's group for its notes comes from the contents tree, the same for the HTML and the EPUB** (`lib/notes.py`'s `groups`, 2026-10-14). Measured on a made-up book of each shape, HTML and EPUB targets, with `numbering: group`, `placement: group`, and `placement: book` each: the two agreed only for chapter files cut at their H2s, the shape the convert suite tested. The HTML took a page's group from the split (`convert.py`'s `page_group`, since gone): a file of its own was a group of one (a book of a file per page: OpenStax's Word books, the CNX books, a Markdown book with `contents`), the Notes page in the files' names' order; a single-file book cut at its H1s was one group, and cut at its H2s or H3s each chapter's own page a group apart, under the source's title; chapter files cut at their H3s numbered a section's subsections apart, the section after them from 1. The EPUB took the contents' top-level entry (`bookassembly`'s `groups`), right in each of those, but a part was one group. Now both take a page's group from the tree both are built from: the top-level entry, a chapter with all its pages or a page on its own, and in a group of `type: part`, the part's entries; groups in the contents' order; a group's title the tree's, numbered when the book is. A part is declared, not guessed, since a part with a page of its own and a chapter cut at its H3s are the same shape in the tree. A proposal weighed and dropped, the split's groups for a split page and the innermost contents group for any other, would have carried the HTML's split mistakes into the EPUB and broken a chapter cut at its H3s into runs (the contents nest a section with subsections as a group); and the EPUB's groups changed not only for parts, as that proposal supposed, but for a single-file book too.

**A page's notes have a heading over them, and an EPUB chapter's don't** (2026-10-15). Pandoc writes no heading over a page's notes, and the Nu checker warned on every page with notes that their section lacks one. The heading goes after the notes' rule, `<h2 class="footnotes-title">` in the word `notes.title` gives (Notes). On the Notes page, each group's notes are headed by the group's title inside their section, and the page is titled `notes.title`, built as Pandoc's JSON so the title isn't read as Markdown. An EPUB chapter's own notes stay unheaded, since a reading system may show each note beside its reference. Pandoc's reader keeps such a heading and its section, so `htmlrepair` drops it on reading a page back, and converting the pipeline's own pages is still a fixed point. A deck's page gets the heading as a book's does.

## HTML pages and their stylesheet

**A source's own colors are kept readable in dark mode: a text color gets a lighter partner, and a background keeps the light mode's text** (measured 2026-11-09, built 2026-11-10). The failure is general: a color a source sets on its own stays, and dark mode changes only the one it didn't set. So any book from HTML, a web archive among them, from Markdown, or from LaTeX that colors its own text or backgrounds has this wherever its readers' browsers are dark, and _Instrumental Analysis_ is the first real book measured that does, in one table (PANDOC-NOTES, The HTML writer, has the measurements). Four ways were weighed: keep a source's own background and give its text the light mode's color in dark mode too, which keeps what the author made; give a source's own text color a lighter partner for dark mode, worked out at conversion as highlighted code's colors were and written with `light-dark()`; leave a source's own colors out of the pages; or keep a page that has any of them light only (`color-scheme: light`). The first two were built, together (`bin/own-colors.lua`, which `target-blocks.lua` runs for a page and an EPUB). A text color of its own and no background gets a partner for dark mode, written after its own declaration as `color: light-dark(own, partner)`: the color's lightness raised in OKLCH, its hue kept and its chroma as far as sRGB holds it, to 4.6:1 on `#232629`, as `lib/highlighting.py`'s colors for code are; the code that worked those out isn't in the repository, so the filter's is new. A color that reads at 4.6:1 there already keeps itself, and one no lighter than the page's own `#1a1a1a`, black say, which says no more than the text's color, takes the dark mode's `#fdfdfd`, where the least that reads would be a mid gray dimmer than the text around it, as a page exported from a word processor, black on every span, would show throughout. A background of its own, one opaque color, and no text color gets the class `own-background`, for `page.css`'s rule, in `@media (prefers-color-scheme: dark)`, to keep its text and what's in it `#1a1a1a`; what's inside it is left as the source colored it, for that background. Both colors, or a background that isn't one color (a picture, a gradient, one partly transparent), are left, with what's inside. A value that isn't a color or isn't one the filter knows (`inherit`, `currentColor`, `transparent`, a color partly transparent) counts as none for a background and is left for a text color; colors are read as CSS Color 4 gives them, hex, `rgb()`, `hsl()`, and the 148 names, each name checked against Chromium's own value (measured, Playwright 1.63). The filter decides and `page.css` acts on its class, because a plain rule of CSS, `[style*="background"]`, would have taken `background-color: transparent`, common in exported HTML, for a highlight and darkened its text on the dark page. A deck's reveal.js slides don't get it, the step being for `html` and `epub` alone: the repository's reveal.js has one theme, `white`, and nothing in `vendor/reveal.js` follows dark mode (no `prefers-color-scheme`, read); a deck's pages, `html`, do.

## PDF through LaTeX

### Structure and headings

**LaTeX numbers the book, and a page's role is the division command it came from.** Titles carry no numbers, and `numbersections` follows the book's `numbering`. A page's role is written as its division command where the role changes; the source's own copies of those commands survive into the intermediates as raw `tex` blocks and are dropped in the assembler, since dropping them in the Lua filter dropped the assembler's too. Pandoc's template brackets the title and contents with `\frontmatter`…`\mainmatter` and puts `\backmatter` after the body whenever the class has them, so a front page in the body restarted the front matter at page i: the PDF that the author's own Pandoc build makes of an economics textbook draft in Markdown labels three pages i and two each ii to v (2026-09-26). `build-pdf.py` sets `has-frontmatter: false` (`defField` doesn't override the metadata) and opens the book in the front matter from a `begindocument/end` hook (`OPEN_FRONT`).

**Headings below a subsection are set on their own line with Pandoc's `block-headings`, not by redefining `\paragraph`.** A heading at `\paragraph` and one at `\subparagraph` with no text after them, followed by the next `\section`, stop a tagged build (LATEX-NOTES, Paragraphs and sections, "A run-in heading followed straight by another heading"); the minimal reproduction is `##### a`, `###### b`, `## c` in a book (2026-10-02, found in DCIC). Pandoc 3.12's template makes these headings free-standing only with `block-headings`, and with it the error goes; `build-pdf.py` sets it unless the metadata file does. Display headings made by redefining `\paragraph` worked too, but would be specific to a class.

### Images, tables, and boxes

**A decorative image stays an `Image` in the tree, with a command around it that marks it an artifact.** It first came out as a figure anyway: the filter's `alt=""` for HTML reaches the LaTeX writer as `alt={}`, which comes after the `artifact` key and undoes it (2026-09-26; the tagging code's side is in LATEX-NOTES, Floats, captions, and graphics). `pdf-target.lua` removes the attribute and sets the graphic module's `artifact` key in a group around the image, first as `\setkeys{Gin}{artifact}` written out and now as `{\OERArtifactGraphics …}`, which `lib/latexbuild.py` defines as that `\setkeys` wherever the tagging code is loaded, so an untagged PDF builds too. The image isn't replaced by a raw `\includegraphics`, because `makePDF` copies images and rewrites their paths in the AST, and a raw command wouldn't find its file.

**A table's caption is retagged in the finished PDF; captions aren't kept out of the `longtable`, and the fix doesn't wait for LaTeX's tagging code.** latex-lab formats a `longtable`'s caption as a row of one header cell and doesn't tag it as a Caption, and it leaves the repeated head's Artifact inside the table (LATEX-NOTES, Tables; [latex3/tagging-project#1583](https://github.com/latex3/tagging-project/issues/1583)). Three ways were weighed on 2026-09-30: waiting for upstream; a pass with `pikepdf` that retags the caption's `TH` as the `Table`'s first child `/Caption` (its content stays with the same element object, so the parent tree still resolves) and moves the artifact rows out of the table; or keeping captions out of the `longtable`, which loses the association of a table with its caption. The pass was built once NVDA had been heard reading the caption as a row (ACCESSIBILITY-NOTES, NVDA with Acrobat): `lib/pdfretag.py`, under `pdf.repair_captions`, on by default. As weighed, a caption was to be found only by matching the table's caption text from the AST; as built, the book's tables are matched to the PDF's in order, and only when the PDF has as many tables as the book.

**Empty paragraph elements are removed after the caption repair, and a parent tree in a shape LaTeX doesn't write is refused, not rewritten.** `lib/pdfparagraphs.py` (`pdf.remove_empty_paragraphs`) runs after `pdfretag.py`, so an artifact row's ghost content is already gone by then: run on the economics draft's PDF as built before the caption repair existed, it lost 10 Formula elements, all inside the `Artifact` rows of discarded repeated heads, with no content of their own, which the caption repair now removes first (2026-10-02). It refuses a parent tree that's a number tree with kids; LaTeX writes one flat array (checked in the economics draft's PDF and the statistics book's).

**A table too wide for its line is judged by its longest unbreakable piece, and is set smaller by LaTeX's own measure, not in a size chosen from counted characters.** On _Instrumental Analysis_ (2026-10-18), a formula's longest word had been the whole formula, so a column of reactions counted as unbreakable. It's now the longest piece TeX can't break, cut at relations and binary operators outside braces and `\left…\right` (_The TeXbook_, chapter 18), a script part of its atom, a `gathered`'s lines each a piece, with capitals counted 1.5 characters and scripts 0.7 (`formula_pieces` in `pdf-target.lua`). A table whose longest words didn't fit a line was then set in `\small`, else `\footnotesize`, else at `\footnotesize` as narrow as its words let it, and one that couldn't wrap at all kept `l` columns there, since `p` columns at their least widths made the F-test's critical values (35.4) wider, 186 points too wide where `l` columns had been 138; in `l` columns at `\footnotesize` it was 93. The sizes went in a group around the table, `{\small …}`, from `fit_to_line`'s result, since setting an attribute on the table inside `walk` changed a copy. Since 2026-10-22 the two sizes are gone: a table wider than its line is numbered and measured as LaTeX sets it, its spaces narrowed and then its type set smaller until it fits (`FIT_MACROS` in `lib/latexbuild.py`), because a table of numbers outran the counted choice in 12-point type (_Introductory Business Statistics 2e_'s F tables, by up to 172 points in `\footnotesize`). What stands from the first round: a table with widths, its source's or the equal ones the HTML reader gives a table with any cell of more than a paragraph (PANDOC-NOTES, The HTML reader), gets a column narrower than its longest word widened from the columns with room.

**A worked example's steps are laid out by LaTeX's measure, each column of math as wide as LaTeX measures it, not by the filter's counts against a counted line.** A worked example's steps written as one formula are a table whose reasons wrap (`docs/cnx-input.md`), and the filter first chose its layout from its own counts of characters. Two ways to find the line were modeled on 2026-10-22, from LaTeX's widths of each formula, cell, and word in the book's preamble and the filter's own decisions and shares, run in `pandoc lua` on each book's pages: on the 51 tables of steps in _College Algebra 2e_'s first chapter, the 99 in four chapters of _Precalculus 2e_, the 28 in three chapters of _Calculus Volume 1_, and the 29 in two of Volume 2. As the filter was, 7, 32, 6, and 7 of them were set across the line though they'd fit at their own width, and 4, 5, 4, and 14 had a formula or a word wider than its column and were set smaller. With the page's line read from its settings (469.75 points, 79.4 of the filter's characters, less a list's indents, 30 points for one list) and the page's gap between columns (2.03 characters, where the filter counts 3): 0, 7, 0, and 2 across though they'd fit, but 9, 6, 15, and 22 set smaller. The reason is that the line counted short, with the gaps between columns counted wide, had given each column of a table set across it 8 to 20 percent more than its count, by the table's columns and whether it's in a list, which covered the formulas' undercount, and `MATH_ROOM` was tuned with it. _College Algebra 2e_'s first chapter built with the page's line alone (`LINE` 79.427) had 9 tables of steps in smaller type, and the 2 formulas fitted with 70 too, where with 70 it's 3 tables of steps in smaller type and a fourth with its spaces narrowed; the model says 10 tables. With LaTeX choosing by its own measure and the filter's shares kept: none across though it would fit, and 4, 5, 4, and 12 set smaller, none that wasn't before. With LaTeX choosing and setting each column of math as wide as it measures the column's widest formula: only what's wider than the line however its columns are shared is set smaller, 3, 1, 2, and 4. That last way was taken (2026-10-23); the filter's shares (`steps_widths`) remain for a table LaTeX doesn't lay out.

**A table whose source gives no widths is laid out by LaTeX's measure of its cells, not by a better count of its formulas, though the measure is the slower.** Both were tried on 2026-10-23, the faster to be taken if both gave acceptable results, on _College Algebra 2e_'s chapter 3 and _Precalculus 2e_'s chapter 4, in Noto Sans, each in a debug tree writing the fit's decisions to a file, one build at a time: the counts as they were (base), `cell_size` counting a formula with `formula_width` (F), and LaTeX laying out every table whose source gives no widths, as it lays out a worked example's steps, each column one of words (L). F broke formulas over lines that L kept whole: _College Algebra 2e_'s section 3.7, Table 2, the toolkit functions, ∛x after its equals sign (base broke √x too); in _Precalculus 2e_'s Key Equations, "f(x) = ab^{x+c} + d" after its equals sign, which base had whole, and "f(x) = a log_b(x+c) + d", which base broke too; and in its section 4.4, Table 2's labels "f(x) = 2^x" and "g(x) = log_2(x)" beside pairs of numbers with fractions (base too). L broke none of them, set a table in the text's type that base and F set smaller (_Precalculus 2e_'s table of a graduate's debt by month, at 91 percent of its size in base and F, its label "Debt ($)" on two lines), and narrowed two tables' spaces where base narrowed four. So F's results weren't acceptable and L's were. In that round, one build at a time, base, F, and L took 373, 378, and 394 seconds for _College Algebra 2e_'s chapter and 443, 458, and 494 for _Precalculus 2e_'s; L as it ships, which measures fewer tables, took 393 and 451 seconds against the counts' 379 and 451 (the counts with that round's other changes, in a second round that ran L first), and 275 against 270 for _Prealgebra 2e_'s chapter 3. As it ships, L laid out the two chapters as the prototype did, line for line (6,551 lines of text on 236 pages, and 7,360 on 219), measuring 24 of _College Algebra 2e_'s tables where the prototype measured 68. It differs from the prototype in three ways. The counts still lay the table out first (`fit_to_line`), giving LaTeX's first run its widths and a TeX without Lua its layout, where the prototype gave each column its count, or its count's share of the line where they're more together. A table with nothing to wrap by the count (each cell a word, a number, or a formula TeX can't break, `cell_size`'s length its longest word) keeps the writer's columns and the counts' fit, since a measure would set its columns as the writer does; measured, a table of formulas in smaller type ran 3.5 points past its column on the third run (the PDF suite's fit book's Mathcells; the forms unicode-math sets small math in aren't as much smaller as the type). And a formula in a table's words is kept whole where the table fits its line so, and broken where TeX breaks a formula in text where it doesn't, before the table's type is set smaller (the measure keeps a formula's longest part between two of its breaks beside its whole width, which in steps, whose formulas don't break, are the same). A table is laid out so where its source gives no widths, every cell is a paragraph or none, none is across columns or rows, none holds a picture, and it isn't in a table's cell.

**A box's rules in a PDF are artifacts, and neither can be left alone at a page's foot.** The rules are `\OERBoxRule{above}` and `{below}`, each a `\hrule` inside `\tag_mc_begin:n{artifact}`, with a big skip outside the box and a medium one inside, and `\nobreak` toward the box; veraPDF passes, and the PDF suite measures both strokes at 344 points (2026-10-18, on _Instrumental Analysis_). A Word file gets a `w:pBdr` on each paragraph of the box, in its place among the paragraph's properties, which Word draws around a run of paragraphs as one, and a table keeps its own border; checked in LibreOffice 24, not in Word. A description list's long term still runs off the page: enumitem's `style=unboxed` would wrap it, and latex-lab's block module refuses the key under tagging (LATEX-NOTES, Lists and their labels), so it's a documented limit.

**Pictures in a figure's row share one line in a PDF, as the pages set them side by side.** `page.css` sets them side by side with flex, wrapping in a narrow window; the PDF sets them in one line after `\leavevmode`, each its share of the line, 48% for two with 4% between, or its own width where that's less, with `\hfill` between them. Pictures with captions of their own still stack. A float is tagged `/float`, role-mapped, and the row's pictures are one paragraph of it (2026-10-18).

### The page

**OpenStax's page is the PDF target's default for every book, kept in a file of its own, `bin/pdf-layout.yaml`.** It became the default on 2026-10-20 on the condition that the settings be documented and easy to change or copy, so they're a YAML file with a comment on each field, which `build-pdf.py` lays under a book's `pdf.metadata` file and `docs/configuration.md` shows whole. The docs advise 13.5-point type or 1.35-inch side margins where WCAG 1.4.8 (AAA) is the goal, and say what each costs. Measured on whole books, each built from the same pages: _Introduction to Sociology 3e_ is 977 pages on the default page, 1,160 at 13.5 points, and 1,040 with 1.35-inch side margins, its full lines averaging 88.4, 78.3, and 78.8 characters, spaces counted; _Introductory Business Statistics 2e_ is 916, 1,062, and 959 pages, with 54, 81, and 81 lines wider than the text. Margins of 1.3 inches, the figure first proposed, come to just over 80 characters, 80.4 in _Sociology_'s first four chapters and 80.3 in _Business Statistics_', so the docs give 1.35. Paragraphs 1em apart, which 1.4.8 also asks for, make _Sociology_ 1,021 pages.

**The page for WCAG 1.4.8 (AAA) is an alternate file, `bin/pdf-layout-wcag-aaa.yaml`, not the default, and it counts line spacing from the type's size.** The AAA settings weren't wanted for every book, but a file that a person who does want them can adopt in the default's place was (2026-10-20). It takes 13.5-point type over 1.35-inch margins: no reason was found against the type, since _Business Statistics_' tables overrun alike, 81 lines either way, and the type serves a reader with low vision too, where the margins cost fewer pages (1,040 against 1,160, at the default's spacing). The criterion's space-and-a-half has two readings (ACCESSIBILITY-NOTES, What the standards say, WCAG). The page was first built on the one that counts from single spacing; since 2026-10-21 it takes the one that counts from the type's size, W3C's technique C21's, as defensible: 13.5-point type as before; lines 1.5 times the type's size apart, the default's own (`linestretch: 1.25`); paragraphs 2.5 times it apart, top to top (`\setlength{\parskip}{1em plus 2pt}`); and footnotes' and captions' lines 1.5 times their type's size (`\SetSinglespace{1.25}`). _Introduction to Sociology 3e_ is 1,208 pages on it, about 24 percent longer than the default's 975, where the other reading's 1,408 are 44 percent, each built from the same pages, unpacked with the boxes added on 2026-10-20 (measured 2026-10-21). `docs/configuration.md` gives the other reading's three lines.

**The footer under the page number has spacing of its own.** In the default layout's bottom margin of 0.8 inch, the class's `\footskip` (30 points) and a second line at the text's spacing, 18.1 points under it with `linestretch: 1.25`, would have put the footer's line 9.5 points from the paper's edge (2026-10-19). So the footer is set single-spaced, in a copy of the class's `\footnotesize`, since `\maketitle` makes `\footnotesize` `\small` on the title page, and the layout sets `footskip` to 0.3 inch, which puts the line 24 points from the edge, where OpenStax's own PDFs have it at 27.

**A tight list's spacing in a PDF is left as Pandoc and parskip set it.** Pandoc writes a tight list (no blank line between items) with `\tightlist`, which sets `\parskip` to zero inside it, and parskip's lists have no space of their own above them. So on the default page, which sets paragraphs apart by space, a tight list's first item is a plain line under the paragraph before it (18.06 points, baseline to baseline, where paragraphs are 25.28 apart), its items are a line apart, and it has a paragraph's space below it; a loose list has a paragraph's space above and below (25.28), as a page and an EPUB set either list (measured 2026-10-20). On the AAA page a tight list has 20.17 above and 33.62 below. `\renewcommand{\tightlist}{\addvspace{\parskip}\setlength{\itemsep}{0pt}\setlength{\parskip}{0pt}}` would give a tight list a paragraph's space above; with a picture of both to judge by, it was left as it is (2026-10-21). All 524 lists in _Introduction to Sociology 3e_'s pages are tight.

### The build

**A guard that warned when a PDF's page count had changed was tried and dropped, because it could never change a build.** The worry was a PDF built in one LaTeX run saying 0 pages in its XMP, which the pipeline's own builds, measured first, never did. The guard was a hook at `enddocument/afterlastpage` that warned "The page count has changed. Rerun LaTeX" wherever `\PreviousTotalPages` wasn't `\ReadonlyShipoutCounter`, where PDF management is on. Measured on 2026-11-08, through Pandoc 3.13: a document with no heading, no contents, and no tagging ran twice without the guard as with it, and said 2 of 2, its first run's reason "Label(s) may have changed" either way. The label is tagpdf's at the last page (`@tag@LastPage`, its `abspage`), which `\DocumentMetadata` loads with tagging on or off: new on a first run, and changed on any run whose count did, as a document made to lose a page from its first run to its second showed, three runs and 2 of 2 (LATEX-NOTES, XMP and the page count; PANDOC-NOTES, The LaTeX writer, for a tagged PDF). Kept in the guard's place: the PDF suite's check that the preamble book, which has no contents, gives its 7 pages in its XMP, and that the suite's book, which has them, gives its count too (`xmp_page_count`), with a row for it on `docs/testing.md`.

### Math for a screen reader

**A PDF/UA-2 PDF carries its math as MathML structure elements and an attached file, with no alt text and without Office's attribute.** `math/setup={mathml-SE,mathml-AF}` is what PDF/UA-2 asks of a mathematical expression (MathML as structure elements, as an attached file, or both; alt text is asked only of a formula that isn't mathematical: ISO 14289-2, 8.2.5.29.1 and 8.2.5.29.2), and it's what NVDA read best (2026-10-10; ACCESSIBILITY-NOTES, NVDA with Acrobat). `mathml-MS`, the attribute Office's own PDFs carry (OFFICE-NOTES, The PDFs PowerPoint exports), was weighed as an option beside them for a book's PDF and a deck's, and isn't offered: the default should be what the standards describe, and no reader is known to need the attribute in a PDF/UA-2 file (2026-10-15).

**A PDF/UA-1 PDF's math carries Office's attribute by default.** `pdf.ua1_math` defaults to `office` since 2026-10-10, with `alt` kept as a choice. With `alt`, NVDA read a formula's TeX source aloud; with `office` it read the formulas as math, since it reads Office's attribute before anything else (ACCESSIBILITY-NOTES, NVDA with Acrobat). The same hearing found NVDA announcing a header cell's words and nothing of its formula, so the output check names a header cell that holds only a formula, as a note.

## A LaTeX book as a source

**The definitions file is per book.** The fixes that hold for any LaTeX are in the code, and `latex-conversion-macros.tex` holds what one author invented, GIAM's `\suchthat` for one (2026-10-05). The run drafts a sample of the file, with suggestions, to give a person as much help with it as it can (`docs/latex.md`).

**A book's own build system isn't run.** A first release doesn't accommodate books' own build systems: the book's build runs first and its output is the conversion's input, and the run stops when the master reaches a missing file, naming the files and any Makefile (2026-10-05, tested). It follows that LaTeX-to-LaTeX remediation may come out as a version built by TextbookImprover and not an exact equivalent of the author's original, which is accepted. For a pull request to a book's own repository, GIAM's being the case in view, the changes that survive the author's own `make` are the ones that matter.

**Remediating a LaTeX book edits the author's text in place; it doesn't go through Pandoc, and the `latex` target isn't the route.** Whether LaTeX-to-LaTeX remediation should go through Pandoc was weighed on 2026-10-06. The `source` target already edits the author's text in place, so it's the direct route; a LaTeX book's PDF is built from that tagged copy and not through Pandoc (`pdf.from: book`, the default); and the work went into closing the copy's gaps: MathML, the decisions it could only count for lack of a place to write them, the book's other masters, `table/tagging=presentation`, and `table/multirow`. Two of those were measured first: an image behind an author's macro can get its alt text, not only a count, and MathML was a real gap. The `latex` target was parked as a way to remediate, since its reading fixes mostly exist so that Pandoc can read Pandoc's own output; it stays a target of its own, as `markdown` and `asciidoc` are. The two table keys are still on the ROADMAP.

**A header declaration in the tagged copy is in braces and behind a guard, and the author's copy never gets a guess.** The `source` target, when the copy is tagged (`tagging: "on"`, or the book's own `\DocumentMetadata`), writes each table a person decided as `{\ifdefined\tagpdfsetup\tagpdfsetup{table/header-rows={1}}\fi\begin{tabular}...}`: the braces because `\tagpdfsetup` holds until changed, the guard because without tagging it's undefined and pdfLaTeX stops (measured 2026-10-05). A table the author declared is left, and in an untagged copy the decisions are counted and not written. The PDF built from the copy declares the census's header guesses too, as the pages and the PDF built from the pages do, while the `source` copy written for the author declares only a person's decisions (2026-10-06).

**A failed build of a book's own LaTeX stops the run; there's no automatic fallback to a PDF from the pages.** A fallback would hide the failure behind a different book. The run stops with LaTeX's first errors (`latexbuild.first_errors`) and names the way out, `pdf.from: pages` (2026-10-06). Any standard but PDF/UA-2 stops it too, since the copy doesn't do PDF/UA-1's link and math work.

**A package LaTeX's tagging can't take is replaced or worked around in the tagged copy, even where that changes the layout.** titlesec and mdframed raised the question (2026-10-07; LATEX-NOTES, Packages tagging can't take). The rule: change or work around any unsupported package, even if the layout and formatting change, so long as the content is preserved and the run warns of the package and of what will change. TextbookImprover's point is to remediate for accessibility, and leaving the result untagged wouldn't do that. `docs/latex.md` lists what each replacement does.

**A book in an AMS class or memoir gets its PDF's title from the tagged copy, which does at the end of the preamble what the tagging code's own hook does at `\maketitle`.** These classes replace `\title`, and a book with a `\title` and no `\maketitle` lost its title and author (2026-11-10; LATEX-NOTES, Contents in classes of their own). Two other ways were weighed. hyperref's `pdftitle` needs hyperref, which the copy doesn't load beside cleveref and its kin (`HYPERREF_AFTER`), and it would make the title plain hyperref's way, where LaTeX's tagging, given `\title`'s argument, makes it plain itself (`\pdf_purify:nN`, `\thanks` dropped), as for every other class. LaTeX's tagging's own `\title[pdftitle=…]` is the command these classes replace. So where the title module's title and author are still empty, the copy's lines copy `\@title` and `\@author` into them (`texremediate.OWN_TITLE`), for amsart, amsproc, amsbook, and memoir, and for a class of the book's own built on one of them, where the book has no `\maketitle` and names no `pdftitle`; the module makes them plain and sets `/Title`, `/Author`, `dc:title`, and `dc:creator` at the last page, as for the article class. The module's variables are private (`\g__tag_title_title_tl`), in LaTeX 2026-06-01 and 2026-11-01 alike. The lines test that the variables exist, so a release that renames them leaves such a PDF without its title, as before, which the LaTeX suite's class case would show.

**The tagged copy adds language tagging to the author's master, for each page in another language and each passage babel sets in one.** The lines go into the master's preamble, on hooks babel runs as it selects a language (`docs/latex.md`; LATEX-NOTES, babel's passages). Adding to the author's source is right, because an author who runs TextbookImprover on their source expects it to be remediated (2026-11-05). A heading in a language other than its chapter's gets no handling of its own: no case was thought of where a heading should be in one language and its whole chapter in another, and such a heading is the author's to mark in the source.

## Word as a source and a target

**A repair of a copy, before Pandoc reads it, is the place for what Pandoc's Word reader loses.** Four things about bookmarks, all read from `Readers/Docx.hs`: body-level bookmarks are dropped, a bookmark inside a heading loses its name to the heading's id, adjacent bookmarks collapse into one, and a bookmark that only another file links to is removed as an orphan (PANDOC-NOTES, The DOCX reader). `lib/docxrepair.py` makes a copy the reader keeps them from: bookmarks moved into the paragraph that follows (into an empty paragraph of their own before a heading), a zero-width run between adjacent ones, and an invisible link to each unlinked one; the filter removes the scaffolding. The source is never touched, and running the filter by hand on a `.docx` doesn't get the repair. On the statistics book the dead cross-references went from 104 to none, and on the nursing book from 338 to what the export itself omits (as of 0.8, 2026-10-03). A bookmark before a table has no paragraph to move into: the pre-pass reads it and the filter emits it as an anchor before whatever the table becomes, which has to happen ahead of the branch that decides that, since a boxed note is a one-cell table that becomes something else, and it lost its anchor when the emission sat in the data-table branch only. `lib/htmlrepair.py` is the same idea for HTML: an id on an element the HTML reader can't hold one on moves onto an empty span first.

**A list is read back into a quotation only from a Word file that says it was written that way.** The Word target indents a quoted list and records that it did in a document variable, `TextbookImproverQuotedLists`, and reading acts on the indent only where the variable is (`docs/formats.md`, Word output). Measured on 2026-10-03: an author's Word file indents lists for other reasons. The Word corpus's programming book has 75 numbered paragraphs indented past their level, a numbered step's sub-items above indented console output, and without the gate two of those lists were pulled into the console quotes; with it, that book's HTML is unchanged. Two more things from the same measurement. A level whose marker is blank (an item's second paragraph, code, or figure, numbered to keep it in the item) isn't a list's own, so `level_indents` leaves it out: DCIC's `Sharing_and_Equality` had a list outside any quote wrapped in two because an item's quote's paragraphs were marked. And a loose list's items styled Block Text inside a quote make Pandoc's reader wrap each item's content in a quote of its own; the per-item wrappers were at first removed once the list was the quote's, and since later the same day the target writes a quoted list's own paragraphs in Body Text with the quote's indent, since the removal couldn't tell an item's own paragraph from a quote in it.

## Markdown and AsciiDoc as sources and targets

**Markdown holds what the author decided; the filter holds what follows from it.** That's the whole design of the Markdown target, and every finding about Pandoc's Markdown reader and writer (raw HTML chopped per tag, spans dropped, figures with ids as divs, implicit figures, the `smart` non-breaking spaces, math that can't end in `\ `, grid widths rounded to characters; PANDOC-NOTES, The Markdown reader and writer) is handled on one side or the other of that line. A decision is written as markup that reads back to it; a derived thing is left out and rebuilt; what Markdown can't say goes as fenced HTML and comes back whole; column widths ride on the marker div as `widths=`, so tables are pipe tables. The second write is the fixed point for a Word-derived source, because the first pass normalizes Word's residue (paragraphs holding only a non-breaking space, leading and trailing spaces, an escaped `a\.`), and nothing about that is worth a normalization rule; the check compares the second write to the third (as of 0.8, 2026-10-03).

**Raw HTML in Markdown is reassembled, not stripped.** Pandoc keeps it one tag at a time, so dropping tags would turn x² into x2. Each opening tag is joined with its match and read as HTML, then cleaned by the HTML sources' own filters, loaded from their files. Code is never touched, since a code span is a `Code` element with no raw HTML in it; the Jekyll adapter's text-level fixes had to be taught the same rule, because CS168 prints `<img src="/logo.png">` as an example.

**Merging follows `contents`, and a merged file takes its source's name only when it holds every page of that source.** `merge: groups` on a markdown target collapses everything under each top-level `contents` entry into one file, nested the way the book is: a page's own headings continue below its heading, shifted relative to the page's first level, not blindly. Where a file doesn't hold every page of one source, it takes the entry's title, made unique, which is what stops a single-file book's chapters all being called `book.md`. So what a merge produces depends on what the book declares: one source per chapter merges back to the chapters with no declaration; one source per section merges into the guess's chapters (`Chapter-1.md` on the statistics book); one source for the whole book merges by the guess's mostly flat list unless the author declares chapters. That dependence is wanted: inventing chapters from heading depth would make merging disagree with the EPUB and the cartridge, which follow `contents` too.

**A source target is only as good as its round trip on real books, and each book found a different class of fault.** For the AsciiDoc target, the suite's case passed early and the security textbook soon after; the statistics book then found footnotes, figure captions, index link text, and banded tables; the economics draft found footnotes of several paragraphs, front matter, and italic math; DCIC found spans, quotations, divs in list items, and code in table cells (as of 0.8, 2026-10-03). The suite's page holds a case from each, and the measure is `compare-output.py` between the book converted directly and its AsciiDoc read back, plus the second write equaling the third.

**The AsciiDoc target writes much of its output itself, because Pandoc's AsciiDoc writer and reader disagree far more than its Markdown pair does.** Its own are images, figures, quotations, spans, open blocks, anchors, and escapes for text AsciiDoc would read as markup. The findings, all measured, are in PANDOC-NOTES (The AsciiDoc writer, against the AsciiDoc reader), and they're material for upstream reports, to Pandoc for the writer and to `jgm/asciidoc-hs` for the reader.

## EPUB

**The EPUB assembler works around Pandoc's writer where the writer can't be told.** Accessibility metadata is set through document metadata (Pandoc takes it since 3.1.12), so `build-epub.py` computes the claims from the build and no OPF is rewritten for that. But the chapter `<title>`, the footnote numbers, and the per-file `mathml` property after notes move are rewritten in the archive after Pandoc writes it, because the writer offers no plain-text form of a chapter's heading, numbers no note, and has already declared which files hold math (PANDOC-NOTES, The EPUB writer). The archive is rewritten in place, `mimetype` first and stored.

## Slides

### A deck in the pipeline

**A deck is a document of its own kind, and its intermediate keeps Pandoc's own slide conventions.** One file per deck, one intermediate per deck, slides as headings and speaker notes as `notes` divs: those are Pandoc's conventions, and what its PowerPoint, reveal.js, and beamer writers read. What the filter does for pages (tables, images, alt text, math) applies to a deck unchanged.

**Remediating a PowerPoint file edits it in place, as the `source` target does for Word.** The decisions are written into the author's file, and everything else is copied byte for byte. That needs a parse of the deck (`lib/pptxparse.py`), not a reader into Pandoc's tree, which is why remediation, the most important use, could be built first.

**The deck reader is TextbookImprover's own, because no repair of a copy gives Pandoc's PowerPoint reader what it never reads.** Repairing a copy before Pandoc reads it, as `docxrepair.py` does for Word, can't work for a deck: no repair of the file gives back formatting the reader never reads (PANDOC-NOTES, The PowerPoint reader). So it's a reader of TextbookImprover's own (`lib/pptxsource.py`), or a better one upstream, or both in turn. Pandoc 3.14 (2026-11-10) has that work, and the two readers were compared on OpenStax's decks and eight exported from Google Slides (PANDOC-NOTES, The PowerPoint reader, 2026-11-12): 3.14's keeps notes, numbered and nested lists, groups, merged cells, and bold and italics outside tables as the project's reader does, and still loses equations and formatting in table cells and titles (all 73 of OpenStax's equations, and all its formatting, are in cells), underline, strikethrough, ScreenTips, the header flags, the decorative mark, the bullets a notes master gives, and metadata. So the project's reader stays: those are what an accessible copy most needs kept, and the oldest Pandoc the run takes is 3.9.

**A deck's slide is two columns only on a layout made for them, and only where the columns keep its reading order.** Pandoc's slide conventions have columns (`:::: columns`), which its PowerPoint writer puts on a Two Content or Comparison layout, so the reader makes columns of a slide on one of those (its layout's `type`, `twoObj` or `twoTxTwoObj`), each top-level shape in the half it stands in, within a twentieth of the slide's width past the middle (`pptxsource.Reader.columns`, 2026-11-11). Placement alone would make columns of any two shapes side by side, which on a Title and Content slide are more often a picture and its words than two columns of a design; and columns are read left then right, so a slide whose reading order goes back to the left after the right is read in that order, as a person may have decided it in `reading-order.csv`.

**A deck's round trip tests the targets as much as the reader.** Its first run on the suite's deck differed in three places, and only one was the reader's (2026-10-15). The filter clears the row heads of a table no reader declared (`apply_headers`), so a reader of tables has to declare each, as `html-source.lua` does; and Pandoc's PowerPoint writer leaves a notes list's paragraphs to a notes master that gives no bullets, a loss every Markdown deck's PowerPoint file had. Two rules came of it. A sidecar the copy reads can be read again downstream: the filter keys an image's alt text by its path, which matches a deck's own image row, and would have put it over a shape's row, which outranks it in the copy, so `IMAGE_ALT` is empty in a converting run. And the comparison has to treat both decks as the filter treats the first, `math.from_text` included, since the trip's Markdown holds the formulas the filter made from the deck's text.

**A deck's reports write an equation in one line, near PowerPoint's linear format, not as TeX.** A slides run reads decks without Pandoc, which the slides suite's `case_no_pandoc` holds it to, and Pandoc's TeX of a deck's equation takes a stub `.docx` and a Pandoc run per deck, so a run without Pandoc would have had no report, or another kind of row (2026-10-13). The line form (`pptxremediate.equation_text`) carries the structure of OpenStax's 73 equations as their TeX does. What it gives up: the micro sign and mu, and the increment sign and Delta, look alike in it, where TeX shows `\mu` and `\Delta`, which `docs/slides.md` says.

### A deck's copy

**A deck's picture is keyed in `image-alt.csv` by its image's content hash, with no deck's name in the key.** A book's image row is keyed on the image's path, `<page>/media/<name>` (its extension optional), and a deck's pictures would have been `<deck>/media/image3`. But PowerPoint keeps the alt text on the picture, not the image, so one image placed twice can have two descriptions (none of the 201 pictures in OpenStax's decks shares an image within its deck), and PowerPoint renumbers its media when it saves. A key on the content hash, `media/` and the hash's first 16 characters, survives both, as `table-headers.csv`'s key on a table's content does. The design first wanted the deck's name in the key too, since the same cover image is in all 13 OpenStax decks (189 distinct images for 201 pictures). It was left out (2026-10-09), so a row covers every deck: as with tables, collisions shouldn't matter, since the same alt text will almost always apply to both, and it settles decorative images, since a picture copied onto dozens of slides by people who don't use the slide master is marked once.

**A slide's reading order is a person's decision on a drafted row, and no order swaps shapes that overlap.** Reordering the tree is easy; deciding what's right isn't, and keeping the slide's look means keeping overlapping shapes in their order (`lib/pptxorder.py`, `reading-order.csv`). Overlap is judged with each shape's box widened by 4 points and stretched to where its geometry reaches, both from measurement on a publisher's decks (testing only, 2026-10-10). With the margin swept on the first draft: at 0 points 33 of 38 reordered slides were drawn alike by LibreOffice, at 1 point 36 of 38, at 2 points 37 of 38, at 4 points 37 of 37 with 2 slides left as they were, and at 6 points 35 of 35 with 4, so 4 points was kept. After a review's new draft, 36 of 37 were drawn alike: the one, a `borderCallout3` whose line (adj7, adj8) reached across a picture, was put under it, which led to counting what geometry reaches. Then 39 slides were out of order, 36 drafted and written, each drawn pixel for pixel alike at 60 and 150 dpi (16 of 16 controls alike too), and 3 left as they were. OpenStax's decks have no slide out of order.

**A heading made a slide's title in place gets the properties its inheritance set, and no others, where PowerPoint's Set as Slide Title writes them all.** In `lib/pptxtitle.py` the placeholder becomes `<p:ph type="title" idx="4294967295"/>` (a text box gets one added, with `spLocks noGrp="1"`), and what the heading's text inherited is written into the shape's own `lstStyle`, where PowerPoint writes it on every paragraph and run. A property that neither the heading's chain of inheritance nor a title's sets is left out, where PowerPoint writes it: LibreOffice's insets for a body that gives none are 0.25 and 0.125 cm, PowerPoint's 0.254 and 0.127, and written out they moved headings by a fraction of a pixel in 132 renders (2026-10-10). A shape styled by the theme (`p:style`) isn't converted, since which wins in PowerPoint, its style's fill or a title placeholder's inherited one, isn't known; nor is one in a group, on a slide with a title placeholder, or whose id repeats (OFFICE-NOTES, PowerPoint and PPTX, Titles).

**A slide whose title is split or repeated gets the old title with a number, not a guess at a new one.** A slide cut in two, or one whose title another slide in its deck has, is drafted as "Title (2)" and so on. It's better to keep it obvious that the title was iterated on than to guess what a person wants there (2026-10-12).

**A restricted font is kept by default, and its replacement is a font the deck already names.** `fonts.restricted` defaults to `keep`: the run warns, says how many decks use the font, and points to the setting that replaces it on the next run (2026-10-10). With `replace`, the font is the one `fonts.replacements` names, else the nearest the deck already uses, by PANOSE, and never a font embedded for the purpose: an embedded font is a subset, the characters it already sets, so a replacement that's only embedded won't hold the text it takes over unless it's installed (OFFICE-NOTES, PowerPoint and PPTX, Fonts).

**A title bold in all its runs is read as bold.** Such a title, as a deck saved from ODP has them, reads as `## **Title**`, where bold that a title inherits from its layout isn't read as emphasis (`docs/slides.md`: "What a placeholder's text takes from its layout or master, a title's bold, say, is the deck's design, and isn't read as emphasis"). Reading a wholly bold title as plain would treat the two alike and change every deck with such titles; it was weighed, and the reading stays (2026-11-04).

### What a deck's targets share

**A deck's targets agree on captions, notes, and a hat, and differ on a bar.** A figure's caption is shown wherever the deck gives one (the page, the PDF, the PowerPoint file); one that repeats the alt text is hidden from a screen reader on the page, its words alone where it holds a note and not at all where it holds an author's link, and marked decorative in the PowerPoint file unless it holds either (Images and media, A caption that repeats its picture's alt text, has how the page hides it, and A deck's PowerPoint file why the PowerPoint file leaves one with a link or a note unmarked); an image that isn't a figure has no caption anywhere; a table's caption is read before the table everywhere and shown above it in the PDF and the PowerPoint file (the page shows it below, `caption-side: bottom` in `page.css`, and reads it first); `slides.notes: omitted` leaves the notes out of the page and the PowerPoint file; and a hat is U+0302 in a deck's copy and in its PowerPoint file (2026-10-12). A bar was the same in both at first, the upper limit with a macron that a deck's copy keeps. Since later that day the `pptx` target writes it as an accent of the macron, as a Word file's is, to be consistent with Word, since the limit gained nothing there (Math, A bar and a hat in Office math; ACCESSIBILITY-NOTES, NVDA in PowerPoint). The copy's bar stays as typed until someone expert with screen readers has gone through every form, with JAWS and VoiceOver too, which hadn't been done as of 2026-10-12.

### A deck's page and its presentation

**A deck's HTML is a plain page by default, and the reveal.js presentation is a target of its own with reveal.js's application role taken off.** A page per deck, the slides as its sections with nothing hidden and no script, is what the HTML target already made of a Markdown deck, and the form that works everywhere: in an LMS, in an EPUB, printed, read top to bottom. Of Pandoc's HTML slide writers only reveal.js was looked at; Slidy, S5, DZSlides, and Slideous weren't, being older and less used. Once a page and a reveal.js sample had been heard with NVDA (2026-10-09; ACCESSIBILITY-NOTES, NVDA in a browser), reveal.js waited, the one thing worth trying being a script of the project's own that removes the role, so NVDA reads the current slide as it reads the page; and since reveal.js's live region would then repeat what browse mode reads, it would go too, or announce only the slide's title. The `revealjs` target, built 2026-10-12, does that in `bin/oer-reveal.js`: the role goes and the live region is silenced (`docs/slides.md`; WEB-NOTES, reveal.js).

**reveal.js is vendored in the repository, and used unless `REVEALJS_DIR` names another copy.** With the repository's copy there's nothing to install, at the price of checking periodically for new releases (2026-10-14). `vendor/reveal.js` holds what the presentations load of reveal.js 6.0.2's package on the npm registry, byte for byte, the package's SHA-512 checked against the registry's `integrity`: `dist/reveal.js`, `reveal.css`, `reset.css`, and `theme/white.css`, the notes, search, and zoom plugins, `package.json`, reveal.js's license (MIT), and Source Sans Pro's (SIL OFL 1.1), about 0.8 MB. Its README, on the pattern of `schemas/cc11/`'s, says why it's there, where it came from, the licenses, that the files stay unmodified, and how to update it: when preparing a release, ask the registry for reveal.js's latest version, and for a new one check its package's hash, replace the files, read what changed against what `oer-reveal.js` relies on, and run every suite with Playwright. `.gitattributes` keeps the files as published (`-text`, and `-diff` for `dist`, so a diff doesn't print minified lines), `.gitignore` lets `package.json` in past `*.json`, and the spelling suite passes over `vendor/` as it does `schemas/`.

### A deck's PDF

**A deck's PDF is built with ltx-talk, not rendered by LibreOffice.** LibreOffice should stay an optional dependency (2026-10-09). LibreOffice's rendering of a remediated PowerPoint file, which would keep the deck's design, was left as a possible option (`pdf.from: libreoffice`) if its results are good and its tagging clean; it isn't built as of 2026-11-11, when `pdf.from` takes `book` and `pages` (OFFICE-NOTES, PDFs LibreOffice makes of PowerPoint decks).

**A deck's PDF keeps a link only on a slide's last step.** tagpdf gathers the links made while tagging is off (ltx-talk's earlier steps) in an Artifact titled "Ignored link annotations", one Link holding them all. `decks.tidy` takes out that bin only (an Artifact holding only link annotations), its annotations, and their ParentTree and IDTree entries, then drops any `/Ref` to an element the tree no longer holds (a table's repeated head the captions' repair removed), and counts marks not tied to a note, which the run warns of (2026-10-11). The trade-off: presenting from the PDF, a link works on a slide's last step only. That was accepted on the condition that it be documented and noted by the run, so a person understands why (`docs/slides.md`).

### A deck's PowerPoint file

**The `pptx` target is Pandoc's PowerPoint writer and a step after it (`lib/pptxtarget.py`), not a route through ODP and LibreOffice.** Measured 2026-10-11 (OFFICE-NOTES, LibreOffice, ODF, and older formats, PowerPoint files in LibreOffice): Pandoc's file passed through LibreOffice loses more than it gains, and from an ODP LibreOffice still dropped the decorative mark and a table's header flag. So a route through ODP would need an ODP writer of the project's own and the same repairs after LibreOffice that a step after Pandoc's writer makes anyway, and it would make LibreOffice a requirement of the `pptx` target.

**A PowerPoint deck's `pptx` target rebuilds a deck only on a template, and no separate setting allows it.** Rebuilding a PowerPoint deck through Pandoc's writer loses the deck's design, which its copy (`format: source`) keeps, so the use for it is moving decks onto a template. The target writes a deck only where `slides.reference_doc` names one, and the run warns what's lost and that this is what the target is for; without one the target writes nothing and the run says why, pointing to `format: source`, and a run whose only targets are such stops (2026-10-15). A `slides.rebuild: true` was considered and left out, since the template already gates the rebuild. If Pandoc's writer improves enough, the requirement can go.

**The `pptx` target cuts a slide in two where Pandoc's writer would draw one shape over another, not where a slide is too full.** The cuts answer where the writer puts things: every picture in the one content area, so over the text after it, a table before it, or another picture, and a new slide with no title at a second table, at a table after a picture, and around columns with text beside them. A table or text too long is set smaller instead (a table down to three quarters of its size, text by the scale autofit records), and warned of past that. None of the real decks has a slide cut (2026-10-12).

**In a PowerPoint file, a figure's caption that repeats its alt text stays on the slide, marked decorative, though NVDA reads it anyway.** NVDA read the alt text and then the caption, not heeding the decorative mark on the caption's text box (ACCESSIBILITY-NOTES, NVDA in PowerPoint). Leaving the caption off would make the output noticeably worse for everyone to accommodate one screen reader's handling of the mark (2026-10-12). A caption holding a link isn't marked, whether the author's link or a note, whose mark the writer writes in the caption as a link to the notes' slide (PANDOC-NOTES, The PowerPoint writer): PowerPoint's mark is a whole text box's, so it would hide the link with the words, where the page can hide the words alone. Such a caption is read whole after the alt text, its words twice, as the page shows a caption with an author's link (2026-11-09 for a note, 2026-11-11 for a link; `deck-pptx.lua`'s `repeats_alt`).

**A 16:9 deck's PowerPoint slides are PowerPoint's Widescreen by default.** `slides.size` defaults to `widescreen`, to match what PowerPoint itself now makes, with `on-screen-show`, the size Pandoc's own files have, as the option (2026-10-12; OFFICE-NOTES, A slide's shapes, styles, and size).

**A table in a PowerPoint file takes a style of PowerPoint's own with enough contrast, Light Style 1 - Accent 1, not a darkened theme color.** Pandoc's writer gives every table the reference document's default (`getDefaultTableStyle`, `Output.hs`), so `ppt/tableStyles.xml`'s `def` is Light Style 1 - Accent 1 (`{3B4B98B0-60AC-42C2-AFA5-B58CD77FA1E5}`): the theme's dark text, a bold header row over a rule in accent 1, rows banded in a pale accent 1 (2026-10-12). In Pandoc's theme (Office 2007's colors, accent 1 #4F81BD) every Accent 1 style of PowerPoint's whose header is white on accent 1, Medium Style 2 - Accent 1, Pandoc's default, among them, or accent 1 on white (Light Style 3), has 4.03:1. Darkening the theme's accent 1 was the first proposal and would have done; a style of PowerPoint's own without the problem was preferred to changing the theme. The styles' ids and families are LibreOffice's (`oox/source/drawingml/table/predefined-table-styles.cxx`, after ECMA-376's `presetTableStyles.xml`). `table_contrast` judges a reference document's default by its family's header colors in its theme (`HEADERS`; a style drawn with tints or shades, or one of the document's own, isn't judged), by WCAG 2's formula, and `convert.py` warns under 4.5:1 with the fix: another default (Set as Default in Table Design's gallery) or a darker theme color.

**A display equation in a PowerPoint file is set off by half a line, and an author's own vertical space is honored: scaled, and added to the space already there.** The half line is the target's own (OFFICE-NOTES, A paragraph's space, and a display equation's). The concern with it was adding space an author isn't expecting, so the space a deck gives in raw LaTeX, a `\vspace` and its kin, which Pandoc's writer drops but the filter sees first, is read and given too (`deck-pptx.lua`, `pptxtarget.paragraph_spacing`; 2026-10-12). It's scaled as a line of the deck's PDF to a line on the slide: ltx-talk's default size is 11pt (`font-size = 11pt` in `ltx-talk.cls`), whose `size11.clo` sets 10.95-point text on 13.6-point lines, beamer's default too; 1em is 10.95 points and 1ex 4.71 (Latin Modern's), so `\vspace{1em}` is 0.81 of a line, `\bigskip` 0.88, and `\medskip` 0.44. The PDF template passes no `fontsize`, and none of the real decks sets one, so it's 11 points always. And it's added, not put in the half line's place, as in LaTeX, where `\[` in vertical mode starts a paragraph (`\nointerlineskip\makebox[.6\linewidth]{}`, latex.ltx) after `\parskip` and the `\vspace` glue, then `\abovedisplayskip`, and where between paragraphs there's `\parskip` plus the glue. So on a sample deck's slide Display Kept, c = d after `\vspace{1em}` has 1.31 lines (`spcPct` 130515), and "then this." after `\medskip` has 0.94.

### Decks in other formats

**A deck in another format (ODP, `.ppt`) is saved as PowerPoint once, and the PowerPoint file is the source from then on.** The original is read once and then set aside, which suits a deck saved once from Google Slides or an old `.ppt`; for someone who keeps editing an ODP in LibreOffice Impress, each change means deleting the PowerPoint file so the next run saves it again, which the run's warning of a newer original prompts. The other way would save the deck into the run's work folder on every run, leaving the ODP the source, at the cost of a copy (`format: source`) that's a PowerPoint file of an ODP deck, sidecars keyed on the ODP's name, and LibreOffice on every run. The first was built, since it's what a person saving the deck by hand would have and the rest of the pipeline is unchanged by it, and it was kept on the condition that the docs make the one-time conversion clear (2026-11-04; `docs/slides.md`).

**An ODP isn't read directly.** Everything that reads, checks, and corrects a deck works on PowerPoint's XML (`pptxparse`, `pptxcheck`, `pptxremediate`, `pptxsource`), and an ODP is OpenDocument's (`content.xml`, `draw:frame`, `svg:desc`, `table:table`), so it would be a second reader, check, and remediator of the same size. Pandoc reads no deck format but PowerPoint's (its readers take `odt` and `pptx`, not `odp` or `ppt`, at 3.12.1). And writing the copy back as an ODP through LibreOffice would add a second trip through LibreOffice's export, with its losses, to every run (2026-11-04).

## Sources from the web, EPUBs, and cartridges

**TextbookImprover owns the container and gives Pandoc pages.** Pandoc's EPUB reader concatenates the spine and rewrites ids on some elements but every link, so a link to a figure or a table dies (PANDOC-NOTES, The EPUB reader). An EPUB, a saved site, an MHTML set, a WARC, and a Jekyll source are all unpacked into a directory of pages that Pandoc's HTML reader reads one at a time. The unpackers write a `project.yaml` with the order they found; the directory is the book from then on, and converting again never goes back to the EPUB or the WARC.

**`raw_html` is on for every HTML page read, or the reader fetches every `<iframe>`.** The price is that every tag with no AST element arrives as a raw fragment, which `html-raw.lua` drops with its contents kept (PANDOC-NOTES, The HTML reader). `<details>` and `<summary>` were dropped with the rest at first, until a Markdown test showed a collapsed answer sitting open; they're kept (`KEEP` in `html-raw.lua`).

**What separates a table of contents from an index is contiguity, not coverage.** Both can reach every page. A contents keeps a page's links together (a chapter, then its sections); an index scatters them (`docs/site-input.md`). The rule's first test passed with the rule switched off, twice: the menu won on size, then a page's self-link gave it the same reach as the index. It proved nothing until the index was the only element reaching every page.

**A plain zip is known by its name; a cartridge and a WARC by what they hold.** Word files, slide decks, EPUBs, cartridges, and WACZs are all zips, so a `.zip` is a plain archive only after the checks that read contents have passed on it, and only by its extension. Extraction refuses absolute paths and `..`, drops the folders that wrap everything, and leaves macOS's litter out. The test for a slide deck first checked only that the deck's parts didn't appear, which they wouldn't have either way, since a zip with no sources stops before anything moves; it now checks what the run said.

**`convert.py` unpacks a web archive it finds alone, and never reads it again.** A WARC or WACZ in a directory with no sources is unpacked there first and its pages converted in the same run. From then on the pages are the sources, because the unpacked directory is where corrections live, so a later run never reads the archive again, and says so. An existing `project.yaml` is kept and the unpacker's goes beside it. A WARC is recognized by its first bytes, not its name, since an upload had renamed both test WARCs. The DCIC crawl converted directly and in two steps agreed on all 80 pages (as of 0.8, 2026-10-03).

**A course is more than its pages, and the cartridge unpacker's report says what else it holds.** Discussions, assignments, web links, test banks, and tool links are reported with where the outline put them, and counted when the outline never names them: OpenStax's sociology cartridge has 42 test banks outside its modules, which are input for the test-bank work when that comes (ROADMAP, Slides and test banks). 22 of its 32 pages are reading lists linking to openstax.org, reported as `links-out`, since converting them converts no reading (LMS-NOTES, Common Cartridge).

**A document a cartridge's page links to is a file unless the author asks.** A Word file the outline names is a page; one a page links to may be a handout meant to be downloaded as it is, so it stays a file, and `--linked-documents`, given when the cartridge is unpacked, makes each convertible one a page beneath the page linking to it. It's decided at unpacking because the unpacked directory is the book: the choice is then visible in its sources and `contents`, not hidden in a conversion setting. Converted, a document brings its defects: two of OpenStax's link to bookmarks they don't contain, which the output check reports and epubcheck calls RSC-012.

**SCORM as a source waits for SCORM as an output.** Only its packaging of HTML content matters here, which reads much as a cartridge does, and the rest of SCORM is authoring tools' scripts (`docs/formats.md`).

**A LibreTexts box is made a div before its page is read, and a numbered formula is written as MathML that carries its TeX.** `lib/libretexts.py` makes each `box-*` section a div with the class `box`, because `html-source.lua` opens every `<section>`, so a box would vanish. A numbered display formula is written as a LaTeX source's numbered formulas are: a `span.equation` holding the TeX in a `<math><semantics><annotation encoding="application/x-tex">`, which Pandoc 3.4 and later read as Math; a `<script>` would close the span (PANDOC-NOTES, The HTML reader). Built on _Instrumental Analysis_, 2026-10-17.

## Languages

**A page's language is worked out once and given to every target, from one sidecar for every kind of source.** `lib/languages.py` decides it (built 2026-10-23): a row of `languages.csv`, keyed by source file as `page-names.csv`'s `source` column is (not by `contents`, which is optional, keyed by page, and has no decks); then the file's own language (a Word file's read as `pptxparse` reads a deck's, the language most of its text is marked with, then its default); then `project.language`. The run reports each page whose language isn't the project's and where it came from, and drafts `languages-new.csv` from the files' own. The package keeps the project's language, and a page in another says so in its HTML, in its EPUB chapter's root (which `build-epub.py` rewrites, since Pandoc's EPUB writer gives every chapter the book's), and in the PDF's `oerlanguage` around its blocks; a copy is written its sidecar's row. The other way weighed was the project's declared language standing over every file's own, the files' languages only drafted. A heading or a passage in another language than its chapter is the author's to mark in the source (A LaTeX book as a source has the same decision for a tagged copy).

**An app's default isn't a decision, so a file's language that's only another region of the project's gives way to the project's.** CS168's theme's `en-US` is the case. The rule applies whether or not the project declares a language, where the design had it apply only to a declared one: the convert suite's cartridge round trip caught the difference, its book's Word pages `en-US` against the default `en` and the cartridge read back declaring `en`, where an undeclared book's pages had been `en` before (2026-10-23).

**A producer's `language` property is trusted over a Word or PowerPoint file's own language, for OpenStax's files only.** OpenStax's Word files are Pandoc's output on OpenStax's own reference document, whose default is `en-US`, and they carry the book's language as a custom property, `language: es`, since Pandoc's Word writer takes the language from `lang` alone (2026-10-20; PANDOC-NOTES, The DOCX writer). So such a file's own language is the reference document's, wrong for an OpenStax book in any language but English and right for an English one by chance, and under the order above a Spanish OpenStax book's Word files would override a declared `es` until a row for each corrected them. The `language` property is therefore the file's language when its `company` property is `OpenStax` (2026-10-23). Other producers are to be added as their files are found to carry the property consistently.

## Headings

**A box's legend stays a heading, and a heading that skips a level is lifted to one below its parent (`heading_levels: outline`, the default).** A legend is a heading in a screen reader's use: H and the list of headings are how a reader skims a page's examples, and a legend made a bold paragraph, or anything but a heading, leaves that list; `role="heading"` with `aria-level` is a heading by another name; and nothing in HTML or DPUB-ARIA marks a box's legend in a way NVDA acts on (`doc-example` isn't a landmark role, and NVDA named even the `doc-` landmarks only generically: Rob, 2026-10-09; ACCESSIBILITY-NOTES, NVDA in a browser, Links and landmarks). So the general rule is the least one. `outline` lifts a heading that skips a level to one below its parent, the nearest earlier heading at a shallower level in the source, and what's under it with it; the page's title is its H1, so a page's first headings are H2 at the deepest; none goes deeper; a deck keeps its levels (its slides and sections), and a Word file's own copy (`format: source`) its styles. WCAG's G141 is advisory under 1.3.1, but the Nu checker calls a skip an error. On _Instrumental Analysis_ (2026-10-18) the rule moved 139 headings on 45 pages, 71 of them a solution or a legend following its parent without skipping a level itself, and the output check's 136 skips and the Nu checker's 68 errors went.

## Packaging

**A project archive is to be a BagIt bag holding an RO-Crate 1.3; the design is settled and not built as of 2026-11-11.** In the design's prototype (2026-11-07, not run again since), bags validated with bagit-python 1.9.0 and came out identical when packed twice, and rocrate-validator 0.13.1 needed w3id.org once, for RO-Crate's context, before it could run offline.

**In the archive's metadata an adaptation's people are to take MARC relators; also settled and not built.** The relators that fit an adaptation are `adp` for an adapter, which the Library of Congress has rewritten to cover modifying a work for a different medium or audience; `aut` for one whose changes substantially alter the work, with the original's authors then `ant`; and `edt` for one who revises it. That's the design's reading of the relators' list and of the Library of Congress's notice (as of 2026-11-06, not checked again since). What Pandoc's EPUB writer does with `aut`, `adp`, and `edt` is in PANDOC-NOTES (The EPUB writer).

**`--includeallhtml` became `--include-all-html`, and the old name is a second, hidden option, not `argparse`'s `deprecated=`.** In `bin/build-cartridge.py`, `--includeallhtml` is out of the help (`argparse.SUPPRESS`), sets the new option, and warns once: "WARNING: --includeallhtml is deprecated and goes after 1.0: use --include-all-html, the same option." `argparse`'s own `deprecated=` came in Python 3.13, and the suites hold the scripts to 3.9. A second name makes `--include`, an abbreviation `argparse` had taken for the old one, ambiguous ("ambiguous option: --include could match --include-all-html, --includeallhtml"), where before the change it appended the page (both measured, 2026-11-06); nothing in the repository uses the abbreviation.

## The audit and the output check

### What a finding is, and what it stops

**The output check never stops the run.** The output exists, and the report is the list to work through; `output-check.csv` existing at all is the signal, like the other reports. epubcheck and the Nu checker are found through `EPUBCHECK_JAR` and `VNU_JAR` or as commands on the path, never required, and their findings go into the same report in the same shape, with the tool's message id as the check. Tool paths are facts about a machine, not about a book, which is why they're environment variables and not settings in `conversion.yaml`.

**The audit depends on `lib/` and Pandoc, never on `convert.py`.** A `bin/` script depends on `lib/` and external programs, not on another `bin/` script, which is what would let the audit split off as a tool of its own. The cost is a second implementation of "image has no alt": the filter reports it from its reading, `sourcecheck.py` from Pandoc's unfiltered JSON. A fixture test holds their counts equal, because two implementations drift.

**A PDF's claim is reported as a claim.** "Claims PDF/UA-2" is a fact about the file (`pdfuaid:part` in the XMP); whether it _is_ PDF/UA-2 is veraPDF's to say, which the audit runs when it finds it (`lib/pdfcheck.py`, `docs/auditing.md`). The simple report is the file's metadata, its claims, and its structural counts, which is enough for triage: tagged, with a structure tree, text and not scans, or back to the source. As of 0.8 (2026-10-03) the metadata and claims sections were described as OctoPDF's; nothing in the repository names OctoPDF now, and that origin hasn't been checked since.

**veraPDF is the PDF validator, optional like the others, and PAC isn't part of the toolchain.** PAC doesn't handle PDF/UA-2 or PDF 2.0 and reports bogus errors (2026-09-26; ACCESSIBILITY-NOTES, Other PDF checkers and viewers).

**veraPDF's WCAG 2.2 profile gates nothing.** The profile is still experimental and gets things wrong (its finding on Roman numerals, for one; ACCESSIBILITY-NOTES, veraPDF), and many users validate against WCAG 2.1 AA or even WCAG 2.0 AA. So passing it isn't a condition of anything, and a run doesn't say that validation in general has failed when a PDF doesn't pass it. The docs say the profile exists and how to add it as an optional check, and its findings are reported where the other checks' are (2026-10-20; `--wcag`, `docs/checking.md`).

**axe-core's findings under `--wcag` are notes, never errors, as veraPDF's WCAG findings are.** `--wcag` stays information, and a run's verdict doesn't depend on what's installed. The case against was that axe-core aims to avoid false positives and veraPDF's heuristics don't, so axe-core's A and AA violations could have been warnings; notes were chosen (as built, 2026-11-06).

### Alt-text rules

**The rule that takes an alt text for a page's title is narrow, and was fitted to what it wrongly named.** A name after a pipe counts only if capitalized and with no bracket in it; an ellipsis only if it follows no comma or digit; the patterns for a title's end read only alt text of 120 characters or fewer (`TITLE_MAX_CHARS` in `lib/alttext.py`); "stock photo" and its kin count only at the end or before a dash or a pipe, where a stock site puts them; and "isolated on white" is no longer a stock site's phrase (2026-10-15). An earlier run over 42,286 alt texts had the rule naming 12, none a title (a matrix's row, a sequence going on, a long description ending with a quotation's author after a dash, a word processor's Stock Images button, a figure isolated on a white background). Narrowed, it names none of the 12, none of OpenStax's 45,427 alt texts (49 repositories, 76 books), none of a corpus of Word books' 2,462, and still the 11 titles and stock captions in a course's decks (18 pictures).

**Alt text that is only a credit is a warning** (`pptx-alt-credit`, `image-alt-credit`, `source-image-alt-credit`, `pdf-figure-alt-credit`). Each sentence opens with a credit's label (`Source:`, `Credit:`, `Courtesy of`, a copyright sign or `(c)` and a year, `Photographer:`), or the text is a list of bylines, licenses, "Own work", and addresses, a byline or an address among them. A license's name alone is a license's badge, and a byline that goes on to say what the picture shows isn't a credit. Measured 2026-10-15: OpenStax's books have none, though many alt texts end with a credit; the Word books, two pictures sharing one credit; a set of course decks written for beamer, sample deck S06's eight (the six CS168 diagrams' credit line, a public-domain line, an own-work byline); another sample deck, one.

**One alt text on different pictures is a note, not a warning, because nearly half the cases looked at were one picture in two files** (`pptx-alt-shared`, `image-alt-shared`, `source-image-alt-shared`). It's reported, case and closing punctuation aside, where no other rule names the alt text. Pictures are told apart by their bytes (`alttext.digest`; a Word file's image by its file in the archive), so copies, and one picture in two pages' files, aren't named; the alt text a sidecar decides is what's compared, so describing one anew settles the other; a deck's pictures are compared within the deck, a run of decks' pages grouped for the output check by `check-output.py --documents`; and a book's image or a deck's picture gets a row of `image-alt-missing.csv` (`shared with 1 other image`). Measured 2026-10-15 on OpenStax's books: 446 alt texts on different pictures within a book, 1,122 pictures in 56 of its 76 books. Of 40 cases drawn and looked at, 21 described different pictures in the same words (`Graph of a cubic function` on 13 graphs; a normal curve's description on a curve with other values; an addition table's on a multiplication table) and 19 were one picture in two files (a JPEG and a PNG, a color and a gray version, a figure with and without its panel letters).

### Pages checked in a locked-down browser

**The lockdown is layers, each stopping something the others don't, and a local run requires fewer of them than a web front end would.** `--wcag` runs axe-core on pages in Chromium, designed on a prototype of 2026-11-01 and added 2026-11-06, and built from the start for the day a web front end runs it on pages strangers upload (WEB-NOTES, Browsers, Chromium, and Playwright).

| Layer | What it stops | Local run | Web front end |
|---|---|---|---|
| Page's scripts blocked by CSP; in a presentation, TextbookImprover's own allowed by hash | Code from the page running at all | Always | Always |
| Route serving the folder | Requests to anywhere else; the page navigating away | Always | Always |
| Resolver rule, no proxy | Name lookups; a proxy | Always | Always |
| Chromium's sandbox | A renderer exploit reaching the system | When it starts | Required |
| Worker's network namespace | Any connection, whatever the browser does | When allowed | Required, or its container's |
| Container: non-root user, limits, read-only input | Escape; exhausting the machine | Not used | Required |

**The parent never touches the browser.** `check-output.py` or `audit.py` starts a worker (`lib/lockedbrowser.py`), hands it the job as JSON, and reads the results back as JSON. The parent enforces the time limits, kills the worker's process group if it overruns, and caps what it reads back (markup excerpts at 200 characters, elements listed per rule), so a page can't swamp the report. The same worker, unchanged, is what a web front end would start in its container.

**A window is held to 4,096 pixels a side, and each step of opening a page has a time limit.** An independent review of the lockdown, before it was added on 2026-11-06, found one denial of service: a deck's own `width` and `height` set the window, with no upper bound, and a page 104,000 pixels square made Chromium stall opening it, or crash, taking the other pages being checked with it; with no time limit on opening a page, the run waited out the worker's whole time (`MOST_PIXELS` in `lib/axecheck.py`).

## The test suites

**`util/compare-output.py` is the regression gate for anything touching the pipeline.** `Runs agree` was the done condition for the Python rewrite of the driver, and is the done condition for the Markdown round trip and for converting the pipeline's own HTML. It matches tables by position, so one inserted table reports every later one as changed: known noise, not a finding. It's also how the routes to one book were compared (CS168 as a saved site, a WARC, and its Markdown), which works because every unpacker names a page the same way from its URL or path.

**A cartridge the pipeline built is the cartridge reader's round trip.** A fixture book packaged, then converted directly, gives the same pages and files, once a directory every web-content file shares (the packager's content prefix) drops out of the book's paths. The unpacker had put every image under the prefix, which the page comparison can't see and the file comparison can.

**The header suites build their Word documents as OOXML directly, not through `python-docx`.** `tests/run-census-tests.py` covers the header guess, and `tests/run-headers-tests.py` the pre-pass end to end. The guess turns on whether formatting is present, and a library that helpfully applies a table style decides the answer before the rule runs. Every condition in the rule was checked by breaking it, and each break failed exactly one named case. The census suite also reads HTML tables through Pandoc and `view_from_pandoc`, skipping without Pandoc.

**The OOXML builder must write a `w:tblGrid`.** Word always does, and Pandoc's reader takes the column count from it; without one, a table whose first row is a single spanning cell reads as one column wide, and a whole case tests the wrong shape while passing. The builder in `tests/run-headers-tests.py` writes a grid with widths, and the filter tests share it instead of keeping a second copy.

**A suite's fixtures are built with what the project already depends on.** The restyle test first built its documents with `python-docx`, which isn't a dependency of the project and happened to be installed where the test was written; on a machine without it the suite failed with "No module named docx." The documents are written by Pandoc now: a `custom-style` div for a `Title`-styled paragraph, a raw OpenXML block for the empty one Word leaves behind. Rebuilding them that way is what found the attribute-order bug in the utility, because Pandoc's `styles.xml` is ordered differently from Word's.

**The validators' jars belong on the machine that runs the suites before a release.** The check suite's "correct page" fixture is itself validated by the Nu checker when the jar is present, which is how the `role="presentation"` rule surfaced. A future change to what the filter emits that stops being valid HTML will fail on a machine with the jar and pass silently on one without.

**The suites' runs of `convert.py` pass `--quick`, and a check that reads a validator's verdict runs the validator itself.** Every `convert.py` run hands its pages to the Nu checker and its EPUBs to epubcheck (its PDFs to veraPDF), a JVM each, and in the convert suite only three checks read a verdict: timed case by case on 2026-10-09, on two cores, the convert suite took 480 s with the validators and 141 s with them hidden (`docs/testing.md`).

**v0.1 compatibility and its tests stay until after 1.0.** The review of the suites on 2026-10-09 found nothing that tests removed code; the old behavior tested is v0.1's compatibility (fixtures 25 and 27, the leftover `.md`, a caption keyed by position).

**The suites read a PDF's text with pikepdf alone (`tests/pdftext.py`), not pdfminer.six.** The suites' PDF cases need pikepdf anyway (the PDF suite already skipped without it), so pdfminer.six was a second dependency for one job, and two checks skipped without it (2026-10-11). The reader parses ToUnicode CMaps itself (codespace ranges, `bfchar`, `bfrange` with arrays, UTF-16BE, codes keyed by number as pdfminer keys them), falls back for a simple font to its encoding's names (the standard encoding's, WinAnsi as cp1252, Mac Roman, `/Differences` with `uniXXXX` and `uXXXX`), and walks the content with an MCID stack: `/Properties` names resolved, the font saved by `q` and `Q` and set by `Tf` or an ExtGState, a form XObject in the font it's drawn in, its text the enclosing sequence's. On a collection of 738 PDF files (663 distinct, about 3.1 million characters; LuaLaTeX made 451, LibreOffice 191, pdfTeX 17, a few others the rest), every `(page, MCID)` got the characters pdfminer.six gave it; two damaged files don't open. The same held on 118 of them under pikepdf 8.7.1, Ubuntu 24.04's, with Python 3.12, as under 10.13. The two checks are unconditional now, and `docs/installation.md` has no pdfminer.six row.

**The presentation's checks need a real browser, so Playwright is optional and the checks skip without it.** Playwright and Chromium are a large dependency for one group of checks, and a test without a browser was weighed (2026-10-12). None would do the same: fitting and the page view depend on the browser's layout, and focus and keys on its behavior. A JavaScript engine with a stand-in page, Node.js say, could test the script's logic with made-up heights, but it's still a dependency, and it would have missed what mutation runs found only in a real layout: the centering after fitting, which reveal.js's own layout on the page's load hid, and where the page view puts a slide and starts its page. So the checks stay in a browser, and a machine without Playwright skips them and says so; they're run with Playwright before a change to the presentation goes out.
