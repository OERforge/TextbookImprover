# Office notes

What Word, PowerPoint, Excel, LibreOffice, and Keynote do, and what their file formats (OOXML and ODF) hold, as read from the specifications and the files themselves or established by test, for the questions TextbookImprover keeps asking. What Pandoc's readers and writers make of these formats is in [PANDOC-NOTES.md](PANDOC-NOTES.md); what a screen reader says in Word or PowerPoint is in [ACCESSIBILITY-NOTES.md](ACCESSIBILITY-NOTES.md); why TextbookImprover writes its Word files and decks as it does is in [DESIGN-NOTES.md](DESIGN-NOTES.md). Each entry says how its fact is known and when, as [README.md](README.md) describes.

## What the OOXML formats share

**OPC allows a part in UTF-16, and PowerPoint writes none.** `pptxparse.part_text` reads a part in its own encoding, and `encode_part` writes it back in that encoding (2026-10-10).

**An accent that names no character is a hat.** ECMA-376 takes an `m:acc` whose `m:accPr` names no `m:chr` as an accent of U+0302, and that's the form of Office's own hat: a ŷ made in Word is such an `m:acc` over a plain `y` in Cambria Math (read in a file made in Word, 2026-10-11). Word stores the letter as typed, where OpenStax's decks hold math italic characters. Pandoc's texmath reads the accent as `\hat{y}`.

**Office's own bar is its overbar structure, `m:bar` with `m:pos` top, not an accent.** Read in a deck holding an X̄ made in PowerPoint (2026-10-10).

## Word and DOCX

### What Word does to a file it saves

**Word rewrites a package when it saves it, rather than editing it.** Measured on one OpenStax chapter opened in Word, converted through the Accessibility Checker's prompt, and saved (for 0.8, 2026-10-03), so the diff is much wider than the conversion: thirteen of twenty-one parts changed. `document.xml` grew from 68 KB to 78 KB with no table altered, `numbering.xml` nearly doubled, `footnotes.xml` more than tripled, an `endnotes.xml` appeared, an empty `comments.xml` disappeared (the source had zero comments; nothing was discarded), and every `docProps` part changed.

**Word renames media parts.** In that round trip, `rId28.so`, `rId38.so`, and `rId51.so` came back as `image1.so`, `image2.so`, and `image3.so`, so a key derived from an image's part name or path doesn't survive a trip through Word (for 0.8, 2026-10-03). `image-alt.csv` keys a Word file's picture on its path, a row still applying where the path differs only by extension (`docs/sidecars.md`, "Sidecar files"); what a run makes of a sidecar's rows after Word has saved the file hasn't been measured since.

**The table key survives a trip through Word.** All six of the chapter's tables came back with identical classification, dimensions, and identical SHA-256 over cell text plus row count, column count, and per-row cell counts (for 0.8, 2026-10-03; the key is `lib/tablecensus.py`'s). That's one chapter, unedited by a person, so it tests Word's rewriting rather than anyone's editing; but it was the failure expected, and it didn't happen.

### Compatibility mode

**What puts a file in Compatibility Mode is the `compatibilityMode` setting, not its namespace.** An answer in Pandoc's issue [#5358](https://github.com/jgm/pandoc/issues/5358) identifies the older flavor of docx Pandoc writes with the `http://schemas.openxmlformats.org/wordprocessingml/2006/main` namespace, and that namespace isn't what puts a file in Compatibility Mode. Checked: the mode-12 OpenStax chapters, the mode-15 book that isn't OpenStax's, a chapter Word itself converted to mode 15, and Pandoc's own output all declare that same namespace, and none uses the Strict namespace. Every Transitional `.docx` uses it. What Word reads is the `compatibilityMode` compat setting, which Pandoc's reference document omits entirely (PANDOC-NOTES, the DOCX writer).

**Word's Convert writes the current generation's whole compat block, not just the mode**: `compatibilityMode 15` plus `overrideTableStyleFontSizeAndJustification`, `enableOpenTypeFeatures`, `doNotFlipMirrorIndents`, and `differentiateMultirowTableHeaders` (measured in the round trip above, for 0.8, 2026-10-03). `util/docx-compat.py` sets the mode and leaves the source's other settings alone, so the two operations aren't equivalent, and the setting is described as declaring the current layout rules rather than as converting the document. _Economics_' Table 7.14 renders the same either way.

**Mixing a new setting into an old mode is something Word itself does.** All 1,011 OpenStax files pair `compatibilityMode 12` with `useWord2013TrackBottomHyphenation`, a Word 2013 setting, and have opened without complaint for years (for 0.8, 2026-10-03). So an upgraded file carrying an older setting isn't an unprecedented state.

**There are two different things inside `w:compat`.** `compatSetting` elements are named key/value pairs; option elements (`doNotExpandShiftReturn`, `useWord2002TableStyleRules`) are bare flags pinning individual layout behaviors, and Convert clears those. Across all 1,027 files in the Word corpus's five books there isn't one option element, only `compatSetting` (for 0.8, 2026-10-03). So on that corpus an upgrade can't leave a stale override behind. `docx-compat.py` reports any it finds and warns before upgrading past one, since another book may differ.

### Images, captions, and tables

**Word's own decorative image has a `wp:docPr` with no `descr` and no `title`.** Read in a file whose image was marked decorative in Word (2026-10-03): the one difference in the XML was that TextbookImprover's file had Pandoc's empty `descr` and `title` beside the mark. The Word target (`docxtarget.apply_markers`) and the Word source remediation (`docxremediate`, which had put back an empty `descr`) both leave a decorative image's `docPr` with neither, as Word does. Word's file and TextbookImprover's both passed Word's Accessibility Checker with no errors (Rob, 2026-10-03).

**Word won't let a hand-made caption go without its number, even with the label removed** (Rob, in Word, 2026-10-03).

**Word's "Mark as layout table" leaves no marker in the file.** Word's Accessibility Checker flags a table with no header row and offers "Mark as layout table" as a fix. Measured by marking two tables in a generated sample document with Word for Microsoft 365 and diffing the package (for 0.8, 2026-10-03), the only change to either table is that the `w:tblStyle` reference is removed and `w:tblLook` reverts to Word's default `04A0`. Nothing else, anywhere: no `w:tblCaption`, no `w:tblDescription`, no `extLst`, nothing in `settings.xml`, no new part, no element in any namespace that wasn't there before. "Mark as layout table" means "stop styling it as a data table", and the file records no claim about layout at all. Three consequences. TextbookImprover can't detect it, so there's no disagreement to report and no way to warn anyone. It also can't be misled into emitting `role="presentation"`, because there's no declaration to honor. And the fix silently destroys evidence: on a table so marked, the census's evidence went from `style=Table; header-looking row 1` to `tblLook:firstRow; tblLook:firstColumn; header-looking row 1`. The bold survived only because it was direct run formatting; a table whose header shading comes from its _style_ would lose the signal the guess reads and drop to `none`, with nothing in the file to say why. The user also loses the table's visible formatting, which is what they'll notice (`docs/troubleshooting.md` has the advice).

### Language and characters

**Word shows a text's language in its status bar and in Review > Language > Set Proofing Language, which sets it for a selection.** That's by Microsoft's documentation, not checked in Word (2026-10-20). A custom property, such as the `language` property OpenStax's Word files carry, shows under File > Info > Properties > Advanced Properties, on the Custom tab, where it does nothing. `settings.xml`'s `w:themeFontLang` picks the theme's fonts rather than saying the text's language, as far as is known, and a copy whose default language is changed leaves it as it was (still `en-US` in a copy made `es`, measured 2026-10-23).

**Word can keep the Symbol font's codes in Unicode's private use area.** Saving text set in Microsoft's Symbol font, Word can keep the font's codes, which it writes at F000 and the code (U+F061 for the font's alpha, 0x61), and which no other font draws: a page or an EPUB showed a box or nothing, and a PDF left each out, saying so (2026-10-21). `cnx.emit`'s `SYMBOL_FONT` gives each of the font's codes the character it stands for, and the report says each was taken as the Symbol font's, since a dingbat font, Wingdings say, writes its characters there too.

### Building a `.docx` fixture without Word

**python-docx gets most of the way, with four traps** (for 0.8, 2026-10-03). It doesn't create `Title` or `Author` paragraphs unless you `add_style()` them first, and without them Pandoc reads no metadata (PANDOC-NOTES, the DOCX reader). It sets a media part's content type from the file extension, so Word's real-world `application/octet-stream` has to be forged by rewriting `[Content_Types].xml` after saving. It deduplicates identical images, so two `add_picture()` calls with the same file give two drawings and one media part. And its `core_properties` are written correctly, but Pandoc ignores them. Equations need no Word either: an `m:oMath` element injected as raw XML after saving is read as a `Math` inline, which is how the vertical-bar case is tested. `tests/make-filter-fixtures.py` builds the suites' fixtures (`docs/testing.md`, "Extending them").

## PowerPoint and PPTX

### A slide's shapes, styles, and size

**A slide's shape tree is its reading order and its stacking order at once.** A screen reader reads the shapes in tree order, and PowerPoint draws them in tree order, each over the ones before it. Microsoft says as much of the Selection Pane: changing the order of objects can affect how the slide looks when objects overlap (2026-10-09). So a reading-order row is written into a copy only where two shapes that overlap keep their order relative to each other (`docs/slides.md`, "The copy").

**A preset shape can draw past its box, and ECMA-376's preset definitions say where.** A callout's tail or line, a connector's bend, and a freeform's points can lie outside the box the shape is given: a `borderCallout3` whose line, by its adjustments, reached across a picture its box didn't touch made its slide render differently once the two were swapped (2026-10-10). LibreOffice's `share/filter/oox-drawingml-cs-presets` has the definitions as text, and python-pptx's `spec.py` the defaults. The reading-order rule's test of overlap counts that geometry (`pptxparse`, under "Preset shapes drawn past their box").

**A slide's text box inherits the presentation's default text style, not the master's `otherStyle`.** A test deck built on Pandoc's template, its default text style 40 points and its master's other style 10, showed its text box at 40 points in PowerPoint (Rob, 2026-10-10) and in LibreOffice, which had shown 18 for an earlier test deck with 18 and 10 points. Apache POI takes `otherStyle`, as far as is recalled; not checked. In a course's ten decks the two styles are the same. `pptxtitle` reads a text box's formatting from the default text style.

**PowerPoint wouldn't open a deck with no theme, `presProps`, or `viewProps`.** A test deck made with the suites' builder, whose decks have none of the three, got "can't read" (Rob, 2026-10-10); rebuilt on Pandoc's template, it opened. The builder's decks are for the suites alone.

**A new deck is Widescreen, 13.333 by 7.5 inches, since PowerPoint 2013, and was On-screen Show (16:9), 10 by 5.625, before.** The two have the same shape. Pandoc's reference document is the older size (PANDOC-NOTES, the PowerPoint writer), and its text is the same size in points, so larger against the slide (2026-10-12).

**Design, Slide Size names a 16:9 deck of either size Widescreen.** It said Widescreen alike for a deck of 12192000 by 6858000 EMU with no `type` and for one of 9144000 by 5143500, `screen16x9` (Rob, 2026-10-14): the menu lists only Standard (4:3) and Widescreen (16:9). Custom Slide Size's "Slides sized for" is where On-screen Show (16:9) should show; not checked.

### Titles

**PowerPoint's Accessibility pane offers Set as Slide Title for one missing title at a time.** After one was set, saved, and the file reopened, it was offered for the next; otherwise the pane offers Add Slide Title or Add Hidden Slide Title, each followed by Approve (Rob, PowerPoint for Windows, 2026-10-10). It was set on three slides of one of a course's decks, each on a different custom layout, and duplicates of the three were given hidden titles; the next two entries are what PowerPoint wrote, read from the saved file.

**Set as Slide Title turns the heading placeholder into the title in place.** `<p:ph type="body" sz="quarter" idx="10"/>` becomes `<p:ph type="title" idx="4294967295"/>` (no placeholder on the layout to inherit from), the shape keeps its id, name, position, and place in the tree, and its inherited formatting is written out in full so nothing changes to the eye: `spPr` gets `prstGeom rect`, `noFill`, a line with `noFill`, and `effectLst`; `bodyPr` every attribute (insets, `anchor="t"`, `wrap`, `noAutofit`); each paragraph's `pPr` every property (`marL="0"`, `algn="l"`, spacing, `buNone`), where the master's title style says `algn="ctr"`, spacing 0, and 44 points; each run's `rPr` every property (72 points, bold, `tx1`, Avenir Next). That's the layout placeholder's list style laid over the master's body style, over PowerPoint's defaults. The other shapes are untouched (read 2026-10-10). A `source` copy makes a slide's heading its title the same way (`pptxtitle`; `docs/slides.md`, "The copy").

**Add Hidden Slide Title adds a title placeholder above the slide, last in its tree.** It adds a `p:sp` named "Title N" with `<p:ph type="title" idx="4294967295"/>`, at x 1257300, y −1989137, 15773400 by 1989137 EMU (PowerPoint's default title placeholder, 838200 by 365125 and 10515600 by 1325563 on a 13.33-inch slide, scaled to this 20-inch one, and moved above it), `bodyPr anchor="b"`, the text in a plain run, and puts it last in the tree, so it's read last (read 2026-10-10). A `source` copy's added title goes first in the tree (`pptxremediate.add_title`), where it's read first: with a slide's title moved last in its tree, NVDA and Check Accessibility came to it last, and in a copy with the title put back first, first (Rob, 2026-10-10).

**PowerPoint's checker reports no duplicate title once a repeated title has " (2)" added.** In a copy of a deck Pandoc wrote, its slide 32's repeated title given " (2)", Check Accessibility reported no duplicate title, and the title looked like the uncorrected deck's with " (2)" added (Rob, 2026-10-10).

### Fonts

**A deck that embeds a font for Preview & Print opens read-only where the font isn't installed.** Each embedded font is an EOT (`ppt/fonts/fontN.fntdata`, flags subset and MicroType Express compressed), whose header copies the font's OS/2 `fsType`. Read in a course's ten decks, made on a Mac (2026-10-10): Avenir Next's is 0x0004 in all six decks that embed it; Georgia's and Candara's 0x0008 (Editable), Montserrat's and Roboto's 0 (Installable). Microsoft: with Preview/Print, "on a computer that doesn't have the font installed", the presentation "can only be opened for viewing and printing, not editing" ([Some of your fonts can't be saved with the presentation](https://support.microsoft.com/en-us/office/some-of-your-fonts-can-t-be-saved-with-the-presentation-2ba26947-5d18-4eb3-b5a9-67a58629e1b8)). Avenir Next comes with macOS, so the decks open normally on a Mac. The theme's fonts are Calibri; Avenir Next is set run by run. A copy that keeps the font opens read-only too. A font's permissions are its license's and are never changed: `pptxfonts` reads them, the run reports the font (`pptx-font-restricted`), and `fonts.restricted: replace` puts another font in its place and takes its embedded files out of the copy, which then opens for editing (`docs/slides.md`, "Fonts").

**A deck that uses a font without embedding it shows a substitute where the font isn't installed, and saving it with Embed fonts on warns.** All ten of the course's decks use Avenir Next, run by run: six embed it (Preview & Print), and four use it without embedding it, one of them in 139 runs. That one opened for editing, and on saving it PowerPoint said "Font Not Available" for Avenir Next, and then kept only Georgia embedded of the five fonts (Rob, 2026-10-10). The run reports such a deck as `pptx-font-unembedded`.

**By PANOSE, the nearest font to Avenir Next that every one of those decks already uses is Arial.** PANOSE is in each `a:latin`'s `panose` and in each embedded font's header. Two of Arial's ten digits differ (weight and proportion); Georgia, a serif, is next; Montserrat, visually the nearest (a geometric sans), has no PANOSE (zeros, as open fonts often do), and neither has Calibri in these themes (read 2026-10-10). Avenir Next LT Pro, the same design, is one of Microsoft 365's cloud fonts, which subscribers' Office downloads and needn't embed ([Cloud fonts in Office](https://support.microsoft.com/en-US/Office/fonts/cloud-fonts-in-office)); Avenir Next itself and Montserrat aren't.

### Tables, links, and media

**A PowerPoint table's headers are two flags, `firstRow` and `firstCol`.** That's all PowerPoint has: no scope, and no headers list. A `source` copy writes a table's header row and column as those two (`pptxremediate`).

**PowerPoint stores a ScreenTip from its own dialog as `tooltip` on `a:hlinkClick`** (read in a deck made in PowerPoint, 2026-10-10), which is where a `source` copy writes one.

**Decks from Google Slides and PowerPoint 2011 for Mac hold links in their speaker notes, and PowerPoint opens such a link only from Notes Page view.** The markup the two apps write (measured 2026-10-15): Google Slides' exports a run `<a:rPr lang="en" u="sng">` with a `solidFill` of the theme's `hlink`, its relationship the notes slide's (`rId2` there, Google's notes slides having no relationship to their slide); decks saved by PowerPoint 2011 for Mac a link pasted with its formatting (`u="sng"`, `tx1`, Arial) or a bare address as a link (`<a:rPr lang="en-US" dirty="0" smtClean="0">`), relationships from `rId3`. In PowerPoint, stand-in decks with each app's markup both open, their notes' links styled as links, opening from Notes Page view and not from the notes pane in Normal view or from Presenter View; a deck from Pandoc's writer, which takes the links out of notes (PANDOC-NOTES, the PowerPoint writer), opens with its notes' words neither styled as links nor opening anywhere (Rob, 2026-11-04, version not given). LibreOffice 24.2.7 reads stand-ins of both as links, each notes page holding two `text:a` once converted to ODP; its PDF export with notes pages puts their link annotations on the slide's page instead of the notes page. The `pptx` target writes a link in the notes to an address as a link (`pptxtarget.notes_links`).

**What a link from a notes slide to a slide should be isn't settled.** By OPC its relationship is `../slides/slideN.xml`, which LibreOffice 24.2 reads as a file (and `slideN.xml`, by OPC a part beside the notes slide, as the slide), and what PowerPoint does with either is untried (2026-10-15). So `pptxtarget` leaves such a link its words.

**PowerPoint keeps a video's captions as a WebVTT file in the deck.** Read in a deck whose video was captioned in PowerPoint with Insert Captions, the video taken out for size (2026-10-10): the captions are `ppt/media/track1.vtt` (`text/vtt`), related to the slide by `http://schemas.microsoft.com/office/2017/04/relationships/track`, and listed in the clip's media extension: `p14:media`'s own extension list holds `p173:tracksInfo` (`displayLoc="media"`, ext uri `{3AFAAA56-56D3-431D-BCD4-E75A35582382}`), whose `p173:trackLst` has a `p173:track` with an id, a `label` (the video's name), a `lang` (empty), and `r:embed`. [MS-PPTX] documents the Track part (2.1.3) and the extension (2.2.4.1); its CT_Track wasn't read. `pptxparse` reads each track, and a clip with a track holding a cue isn't reported as uncaptioned.

### Equations

**PowerPoint's own Fallback for a shape holding an equation is the same shape filled with a picture of its text, locked against editing** (read in a deck made in PowerPoint, 2026-10-10). A program that doesn't take the Choice, LibreOffice among them, shows the Fallback. The `pptx` target gives each shape or table holding an equation a Fallback with each equation written as a line of text (`docs/slides.md`, "The PowerPoint file").

**PowerPoint shows a display paragraph of two equations as two equations on separate lines.** In a test deck, slide 2's display paragraph of two equations looked as slide 3's two display paragraphs did (Rob, 2026-11-04, version not given). That's how the reader takes it, each of a display paragraph's equations a paragraph of its own (`docs/slides.md`, "Converting a PowerPoint deck").

### A paragraph's space, and a display equation's

**PowerPoint shows a text body's first paragraph's space before it where the body says to respect it (`spcFirstLastPara`).** ECMA-376's `spcFirstLastPara` on `a:bodyPr` says whether a text body's first paragraph's space before (and its last's after) is respected, false when omitted (the Open XML SDK's `UseParagraphSpacing`: "If this attribute is omitted, then a value of 0, meaning false, is implied"), which is what `pptxtarget.body_height` assumes of PowerPoint. On a slide given `\vspace{2em}` at the top of its text, its body told to respect it, PowerPoint showed the space as expected, and on two slides of `\bigskip`, `\vspace`, `\addvspace`, and `\vskip` before text, a list, and a heading it showed each paragraph's space as expected, or about so (Rob, 2026-10-14). LibreOffice 24.2.7 shows no space before a first paragraph, five lines of it, with or without the attribute. So where a deck's space is at the top of a shape's text, the `pptx` target gives it to the first paragraph and sets the attribute, and the text box's top inset isn't needed for text.

**PowerPoint shows no space before a paragraph holding a display equation, however it's given and wherever the paragraph stands, and shows its space after.** In the `pptx` target's first sample decks, display equations weren't set off by any space from the paragraph above (sample deck S26's slide 20 and others), though nothing overlapped (Rob, 2026-10-12). Given half a line before each, S26's display equations still had no space above them, and an equation c = d showed none of the 1.31 lines before it (`spcPct` 130515), where a paragraph of text after it, "then this.", given 0.94, did seem to have its own (Rob, 2026-10-14). One display that looked set off, x̄ = …, is the tallest of them, a fraction over a sum, which may have looked like space; and an equation's paragraph has the same properties as text's in the file. A probe deck then set one gap of about two lines a different way on each slide, every other space set to none: PowerPoint showed no space before an equation, in lines or in points, below text or at the top of a text body that respects it, and showed a paragraph of text's space after, an equation's space after before text, and an equation's space after before another equation (Rob, 2026-10-14). So the `pptx` target gives a display equation's space to the paragraph above it as that paragraph's space after, whether text or another equation: built so, each equation of sample decks S26 and S30 and of the made-up deck was set off from the text above it by that text's space after, an equation after a list too, and c = d by the space after the equation above it, a = b (Rob, 2026-10-14). An equation that opens a slide's text has no paragraph above it, so the deck's space there goes into the text body's top inset (`bodyPr tIns`): PowerPoint shows that top margin about as much as the same space above text, and an equation given none sits higher (Rob, 2026-10-14).

### The PDFs PowerPoint exports

**PowerPoint tags each equation in a PDF it exports as a `Formula` that carries its MathML twice and its words once.** Rob exported a sample deck of 16 equations from a freshly updated PowerPoint for Microsoft 365 three ways (2026-10-15): File, Export, Create PDF/XPS; Save As; and Create PDF/XPS with PDF/A checked. Acrobat's add-in crashed, probably its license or its installation. The first two have the same structure, Save As adding the author; the third is PDF/A-3A, which veraPDF's 3A profile passes, with the same structure. Each equation is a `Formula`, 16 for the deck's 16, with three things. An attribute owned by `/MSFT_Office` holding `/MSFT_MathML`, the MathML as a PDF text string: PDFDocEncoding when it's ASCII, UTF-16BE with a byte order mark when it isn't (`x̄`'s bar, `∑`, a Greek letter). An associated file, `equation-N.xml`, `/AFRelationship /Supplement`, subtype `application/mathml+xml`, the same MathML in UTF-8, listed in the document's embedded files too. And `/Alt`, the formula in words as Microsoft's math speech says it ("cap E equals m c squared", "x overbar equals 1 over n, sum from i. equals 1 to n of x sub i.", a period after a lone letter so it's said as a letter). A formula alone in its paragraph is `display="block"`, as Office counts it a display, a table's cell holding only one too. Each `Formula` names PDF 2.0's standard structure namespace (`/NS`), in a PDF 1.7 file. The MathML has no spaces between elements, `<mover accent="true">`, the bar U+00AF (as the `pptx` target writes it), the hat `^` (the deck's U+0302 made the spacing character), and letters as the deck holds them (a plain x, math italic Greek).

**PowerPoint's `/Alt` for a formula of one letter loses the letter.** For `s` or `μ` it's "equation,", so a reader of `/Alt` alone hears no letter (read in the same PDFs, 2026-10-15).

**The rest of an exported PDF's tagging.** A slide is a `Sect` (`Slide`, role-mapped), each text box another (`Textbox`); the title slide's title is an H1 and its subtitle a P, every other slide's title an H2, and nothing is a `Title`. A table's head and body are `THead` and `TBody`, its header cells `TH` with `/Scope /Column`, each cell's text a text box's P; the caption, a text box above the table, is a P, not a `Caption`. A header cell holding only a formula is built as one in TextbookImprover's PDFs is, for whose column NVDA in Acrobat announces no header (ACCESSIBILITY-NOTES, NVDA with Acrobat, "Formulas"); PowerPoint's PDF hasn't been heard. The document's `/Lang` is `en`, where the deck's runs say `en-US`. veraPDF's PDF/UA-1 profile fails it on one rule, clause 5, since its metadata claims no PDF/UA, and passes the other 105 (read in the same PDFs, 2026-10-15).

**LaTeX's `mathml-MS` writes Office's form.** `math/setup`'s `mathml-MS` writes an attribute owned by `/MSFT_Office` holding `/MSFT_MathML` (UTF-16), which is how Microsoft Office stores MathML in a PDF it exports, as far as LaTeX's implementation of it shows; added beside `mathml-SE` and `mathml-AF`, it passed PDF/UA-2 too. Word and PowerPoint put MathML in exported PDFs (PowerPoint from Version 2602 on Windows), but Microsoft hasn't documented the form, so whether `mathml-MS` matches what PowerPoint writes could only be settled with a PDF PowerPoint exported. Seen on 2026-10-15: PowerPoint for Microsoft 365 writes that attribute, owner and key, beside an associated file, as `mathml-MS` and `mathml-AF` do together (LATEX-NOTES, "PDF/UA-1 against PDF/UA-2").

## Excel and CSV

**Excel reads a CSV without a byte-order mark as Windows-1252, and adds the mark when it saves "CSV UTF-8".** So an en dash in UTF-8 (E2 80 93) shows as "â€“" and a minus sign (E2 88 92) as "âˆ’", which is how drafts of _Instrumental Analysis_'s alt text looked in Excel (Rob, 2026-10-24) though `image-alt.csv` was valid UTF-8: 49 of 218 drafts held such characters, minus signs, dashes, Greek letters, µ, °, ±, √, Å, ². Every report and every file of rows written to become a sidecar starts with the mark, and a sidecar is read with it or without (`docs/sidecars.md`, "Sidecar files").

**Excel's plain "CSV" is saved in a code page: Windows-1252 by Windows Excel and Mac OS Roman by Excel for Mac, in the US and Western Europe.** That's as others report them (Donat Studios' "CSV: An Encoding Nightmare", 2016 to 2022); not tried in Excel (2026-10-25). The line ends differ too: a CR alone, as Excel 2011 for Mac saved them, and CR LF from Windows, Excel 2016 for Mac ending lines as Windows does, as a Microsoft Q&A thread of 2016-11-30 reports. `sidecars.read_code_page` reads a sidecar's lines that aren't UTF-8 in whichever of the two code pages reads them with fewer characters misplaced, and where they have as many, the line ends decide, a CR alone Mac OS Roman's and CR LF Windows-1252's (`docs/sidecars.md`, "A sidecar that isn't UTF-8").

## LibreOffice, ODF, and older formats

### Running LibreOffice

**LibreOffice needs an absolute `HOME`.** Run headless with a relative one, LibreOffice 24.2.7 gave "Unspecified Application Error" and no PDF (2026-10-09).

**LibreOffice saves an empty file as a blank deck, and `soffice.bin` outlives its wrapper** (LibreOffice 24.2.7, 2026-11-04). So `lib/decksave.py` names an empty file, one that isn't a deck of its kind (a PowerPoint file named `.ppt` or `.odp`, which the run says to rename), and an ODP saved with a password before LibreOffice sees them. And it runs LibreOffice with a profile and a folder of its own, removed after, in a session of its own, so that a save over five minutes stops `soffice.bin` too, which outlived its wrapper when only `soffice` was stopped.

**Without its Math module, Writer drops every equation silently.** The module is the package `libreoffice-math` (LibreOffice 24.2.7, 2026-10-10).

### Office math in LibreOffice

**LibreOffice 24.2.7 reads Pandoc's `\bar`, an accent of U+203E, as an acute accent, and saves it back so.** Measured by opening a Word file of the bar's forms in LibreOffice, its Math module installed, and saving it again (2026-10-10), which no listening with NVDA and Narrator could have shown. It reads an accent of U+00AF as its `bar {X}` and draws a bar accent, and writes its own bar as that accent when it saves a Word file; Office's `m:bar` on top and an accent of U+0305 it reads as `overline`, and an accent of U+0304 as `bar`; and an accent of U+203E, Pandoc's `\bar`, as `acute {X}`, drawn X́ and saved back to Word as an acute accent. So every `docx` target's bar, and every bar the repair wrote before then, was an acute accent in LibreOffice. The `docx` target and a remediated copy write the accent of U+00AF now (`bar_accents`; `docs/formats.md`, "Word output").

**LibreOffice 24.2.7 reads an accent of U+0302 or U+005E as its `widehat`, and one of U+02C6 as `acute`.** It writes its own `hat` and `widehat` to Word as U+005E, and saves U+02C6 back as an acute accent (U+00B4), as it did U+203E; the one character ŷ and a y with a combining circumflex after it in one run it reads as `ŷ` (measured on a Word file of five forms, 2026-10-11).

### PowerPoint files in LibreOffice

**LibreOffice fits shrink-to-fit text anew as it draws, so a shape's place in the tree changes the fit.** On one slide of a course's deck, the body text, a placeholder with `normAutofit lnSpcReduction="10000"`, wrapped and spaced differently once a reading order put it after the title and the table; with the autofit taken out of both, the reordered slide draws pixel for pixel as the original (measured 2026-10-10). PowerPoint, as far as is known, applies the saved `fontScale` and `lnSpcReduction` until the text is edited, so it plausibly shows the slide as before, and in PowerPoint the reordered slide looked good (Rob, on the copy made 2026-10-10).

**LibreOffice 24.2 converts PowerPoint to ODP and back, but the round trip loses Office's formulas**: LibreOffice takes PowerPoint's fallback pictures of them (2026-10-09). PANDOC-NOTES, the ODT reader and writer, has what Pandoc makes of LibreOffice's ODT.

**A PowerPoint file Pandoc wrote loses more than it gains when LibreOffice saves it.** Measured with LibreOffice 24.2.7.2 on six of Pandoc's PowerPoint files (a conference deck, sample decks S05, S27, and S30, one of another course's decks, and a sample deck), each opened and saved again as PowerPoint, compared by the parse and the checks (2026-10-11). Every formula is gone, 88 of 88, with the text boxes holding them (S30's 44 content placeholders are 34 after): Pandoc writes a text box holding a formula as `mc:AlternateContent` whose only branch is a Choice requiring `a14`, with no Fallback (PANDOC-NOTES, the PowerPoint writer), and LibreOffice drops the shape. Every table's `firstRow` is cleared (5 of 5, each now `pptx-table-no-header`), and the other course's deck's tables, whose cells hold formulas, lose rows. One of that deck's three links is lost, the language moves from the default text style onto each run, and each layout becomes a master of its own with its own theme (1 master and 11 layouts in; 11 of each, and 11 themes, out). What it puts right, the undeclared `a14` and the empty shape, the `source` copy puts right already; alt text stays a file name, and an untitled slide stays untitled.

**LibreOffice's PowerPoint file of an ODP keeps a formula, a picture's description, and a link.** A small presentation written by hand as flat ODP (`.fodp`: a title, a nested list with a link, a formula as a native Math object, a described picture, a picture marked decorative, a table using its first-row style, and notes) was saved as PowerPoint with LibreOffice 24.2.7.2 (2026-10-11), which is what an ODP writer of TextbookImprover's would get from it. The formula came out as OMML in `a14:m`, in `mc:AlternateContent` with an empty Fallback, and the picture's description and the link were kept; but the decorative mark was dropped (the picture came out with no alt text, which the check reports), and so was the table's header flag. The title and notes didn't come out as a title placeholder and notes, more likely the probe's doing (it had no master placeholders or notes page) than LibreOffice's. The decorative mark's loss was the probe's doing too: the mark as Impress writes it is kept (measured 2026-11-04; "Decks in other formats, saved as PowerPoint", below).

### PDFs LibreOffice makes of PowerPoint decks

**LibreOffice 24.2.7 renders PowerPoint to PDF headless, tagged by default, with a reasonable structure and nothing for a formula.** Measured with Ubuntu 24.04's LibreOffice. With its PDF/UA option, OpenStax's first deck fails one PDF/UA-1 rule in veraPDF, 7.1 (content neither tagged nor an artifact), once on each of its 27 slides, and a conference deck fails 7.18.5 as well, on its 10 links. The structure is reasonable: a heading for each slide's title, lists as `L`, pictures as `Figure` with their alt text, tables with `TH` from the header row. Its rendering isn't PowerPoint's: a table holding equations was drawn from PowerPoint's fallback copy of the table, whose formula cells are each filled with one picture of the whole table, offset to show that cell's part, and LibreOffice drew the whole picture, shrunk, in every one. With NVDA in Acrobat, its PDFs of OpenStax's decks read well, alt text, table headers, and the text in tables, and gave nothing at all for a formula cell (Rob, 2026-10-09): in OpenStax's first deck, the relative-frequency cells on slides 20 and 21 (3/20 and the like, the deck's only formulas) are each a TD holding an empty paragraph and the picture, with no alt text. The cumulative column beside them is plain text ("0.15 + 0.25 = 0.40"), which is probably what was heard as formulas. So it's an option for a PowerPoint source whose design should be kept, with repairs after it like the PDF target's, or a newer LibreOffice; not the default.

### Decks in other formats, saved as PowerPoint

**LibreOffice opens `.ppt`, `.odp`, and Keynote files, so a deck in one of them can be saved as PowerPoint first.** It opens `.ppt` with its `MS PowerPoint 97` filter and Keynote files with its `Apple Keynote` filter; on 2026-10-11 neither had been tried on a real deck. Since 2026-11-04 a slides run saves an `.odp` or `.ppt` deck as PowerPoint through LibreOffice and reads that (`lib/decksave.py`; `docs/slides.md`, "Decks in other formats"), losing what this section measures on the way. The Keynote filter hasn't been tried since: the docs send a Keynote deck through Keynote's own File > Export To > PowerPoint.

**What LibreOffice's save keeps of an ODP or a `.ppt` deck, measured on 13 decks kept for testing** (LibreOffice 24.2.7, 2026-11-04). LibreOffice saved all 13, eight Google Slides decks downloaded as ODP, three ODP exports, and two `.ppt` decks, in 29 seconds, about two each. ODP exports kept their notes' links (39 and 15), and a Google download's two hidden slides stayed hidden; one embedded object of an ODP lost its picture. The first `.ppt` deck's 8 embedded objects, the ones saved with it being MathType 5 and Equation Editor 3.0 equations, have no picture in LibreOffice's file, so the reader leaves them out; PowerPoint's own Save As keeps an embedded object's picture. Probed on decks made for it: an ODP picture's alt text (`svg:desc`) becomes its description, and its decorative mark, which Impress writes on the picture's graphic style (`loext:decorative`), is kept (`adec:decorative`); a mark on the frame itself, where a first probe put it, isn't, but Impress doesn't write one there. A table's header flag wasn't measured, LibreOffice's own ODP tables having none without a table design.

**LibreOffice gives ordinary slides' layouts the Title Slide type.** An ODP page with no layout of its own, as Impress saves a Section Header, Comparison, Content with Caption, or Picture with Caption slide, gets a layout with `sldLayout type="title"` in LibreOffice's PowerPoint file (LibreOffice 24.2.7, 2026-11-04), so a reader that took a first slide on such a layout as the title slide lost all of it but its title. `pptxsource.bare_title_slide` goes by the slide instead: the first slide is the title slide when its title is a ctrTitle, or when it holds a title and a subtitle with text and nothing else the reader keeps.

**A deck LibreOffice saved has its table style's band written into each cell, and Header Row cleared on every table.** OpenStax's tenth deck saved through LibreOffice and back has the green band in each cell of a blank row at a table's top, and Header Row cleared on every table, so its four tables are reported as having no header row marked, with the same guesses and previews (LibreOffice 24.2.7, 2026-11-04). So a cell's color and borders are its look, not something in it, and a row holding nothing else is blank (`pptxparse.Table.blank_rows`).

**PowerPoint keeps a deck's slide and shape ids, and LibreOffice renumbers them on every save**, the original's or a PowerPoint file edited in Impress. Measured with LibreOffice 24.2.7 (2026-11-04): it numbers a saved deck's slides 256 on, and its shapes, in order through the deck, on every save, so with the first of an ODP deck's 21 slides taken out, every later slide's id moved down one and its shapes' ids by the first slide's count, and one text box added to a slide moved the next slide's shape ids by one. A sidecar row naming a slide or a slide's shape can then name another, its key still there, so it isn't reported; the same ODP saved twice gives the same images, slide ids, and shape ids, so rows keyed on a picture's image or a table's content still find it. The docs say to check such rows after (`docs/slides.md`, "Decks in other formats").

## Keynote and Google's exports

**Keynote 15.4 and an earlier Keynote opened TextbookImprover's PowerPoint deck, and neither opened Pandoc 3.12.1's.** A tester ran the latest Keynote and an earlier one on two decks (2026-11-06), without naming either version. The latest for Mac is 15.4 (Wikipedia, 29 September 2026; no newer release found on 2026-11-06), and the earlier one is likely 14.5, the old app Apple leaves beside 15.1 and later ([Apple](https://support.apple.com/en-us/126151): 15.1 is a separate download, and the 14.5 versions can be kept or put in the Trash), an inference. Both opened TextbookImprover's deck, the presenter notes there and the list slide's link in them ("an example page", https://example.org/notes, in the screenshot), and the formula set as a formula; 15.4 warned "This PowerPoint presentation may look different. … Unsupported media were removed. Slide Layout(s): Picture with Caption", a layout no slide uses, whose picture placeholder, from Pandoc's reference deck, is empty: a likely cause, not tested. The two decks differ in more than the notes' color map (the runs' language, the notes' link's relationship, a formula's Fallback, the slide size and the layouts' geometry, the file's properties, the table styles), so the test shows TextbookImprover's deck opens, not which difference Keynote needed. PANDOC-NOTES, the PowerPoint writer, has the report of Keynote rejecting a file with speaker notes, #11935.

**From Google Slides, the PowerPoint download serves better than the ODP download.** Measured on eight decks downloaded both ways, the ODP saved as PowerPoint by LibreOffice 24.2.7 and both read by the pipeline (2026-11-04): the same 311 slides, 17 tables, 152 lists, 25 links, and notes on 48 slides. But the ODP download's titles are bold (132 of 222, and four decks' own), written onto each title's runs where the PowerPoint download leaves it to the layout; the PowerPoint download gives the text a language, which LibreOffice's save of the ODP doesn't; 97 of the PowerPoint download's pictures with no alt text have the image's file name as their description, which the check reports, and the ODP's have none; and the ODP's title slide is a title beside a subtitle on a Title Slide layout, which the reader didn't take as the title slide until `pptxsource.bare_title_slide` ("Decks in other formats, saved as PowerPoint", above). "Tables, links, and media", above, has the markup of a link in a Google Slides export's notes.
